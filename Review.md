# Review

- [P1] Require the custom reduced-pressure executioner before dropping momentum forcing — [WCNSLinearFVConservativeSharpInterfaceFlowPhysics.C](/Users/chowr/Work/projects/single_phase_vof/moose/modules/navier_stokes/src/physics/WCNSLinearFVConservativeSharpInterfaceFlowPhysics.C#L608)
  When this sharp-interface physics is used under the stock `PIMPLE`/`SIMPLE` executioners, `split_momentum_predictor_operator` (now defaulted on) removes the pressure/body-force kernels here and in `addMomentumReducedPressureKernels()`, but only `ReducedPressurePIMPLESolve::addMomentumPredictorExplicitForcing()` adds those terms back. The result is that stock segregated solves — and every steady case, since this patch adds no reduced-pressure SIMPLE executioner — will advance momentum without pressure/capillary forcing.

- [P1] Evaluate wall predictor accelerations on the boundary face itself — [ConservativeSharpInterfaceRhieChowMassFluxBase.C](/Users/chowr/Work/projects/single_phase_vof/moose/modules/navier_stokes/src/userobjects/ConservativeSharpInterfaceRhieChowMassFluxBase.C#L556)
  When `surface_tension_face_acceleration` or `transient_projection_face_acceleration` is a face-centered functor (which is the default generated sharp-interface path), this boundary branch queries it with `makeElemArg(...)` instead of a face arg. `FaceCenteredMapFunctor` on an `ElemArg` reconstructs a cell value from surrounding faces, so the wall `phig` term no longer uses the actual boundary-face value/contact-angle correction, and the wall pressure-flux constraint is assembled from the wrong source.

- [P2] Treat partially overlapping Rhie-Chow block sets as overlaps — [WCNSLinearFVConservativeSharpInterfaceFlowPhysics.C](/Users/chowr/Work/projects/single_phase_vof/moose/modules/navier_stokes/src/physics/WCNSLinearFVConservativeSharpInterfaceFlowPhysics.C#L1102)
  If an existing `RhieChowMassFlux` lives on a partially overlapping block subset (for example existing `{1,2}` and new sharp-interface physics on `{2}`), this equality test falls through and a second RC object is created on the shared block instead of reusing/erroring. That gives ambiguous face-flux coupling on the overlap, which is exactly the situation the surrounding guard is trying to prevent.

- [P2] Apply coordinate factors in the new curvature integration path — [ConservativeSharpInterfaceCurvatureCalculator.C](/Users/chowr/Work/projects/single_phase_vof/moose/modules/navier_stokes/src/userobjects/ConservativeSharpInterfaceCurvatureCalculator.C#L403)
  In axisymmetric/RZ cases, these face and volume measures need the usual coordinate weighting (`faceArea()*faceCoord()` and volume times the cell coord factor). This new curvature path uses raw `faceArea()`/`elemVolume()` here (and again in `updateCurvatureMaps()`), so the reconstructed gradients and `K = -div(nHatf)` are scaled incorrectly away from Cartesian meshes.

- [P2] Do not force 0° contact angles on non-dynamic walls — [ConservativeSharpInterfaceCurvatureCalculator.C](/Users/chowr/Work/projects/single_phase_vof/moose/modules/navier_stokes/src/userobjects/ConservativeSharpInterfaceCurvatureCalculator.C#L223)
  In mixed dynamic/non-dynamic wall-angle setups, this fallback seeds every selected boundary with `0` radians whenever a wall-angle functor is present but `static_contact_angles_degrees` is omitted. `contactAngleRadiansForFace()` then uses that `0` value whenever the generated dynamic-angle functor returns `NaN` on a non-dynamic boundary, so those walls silently get a 0° contact-angle correction instead of being left unchanged.
