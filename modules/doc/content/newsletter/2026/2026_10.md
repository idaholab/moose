# MOOSE Newsletter (October 2026)

## MOOSE Improvements

### Apps can now use fewer threads than the process-wide count

The number of threads is now a per-app property rather than a single process-wide count. An app
can request fewer threads than `--n-threads` by setting
[!param](/Application/num_threads) in its `[Application]` block, and its warehouses, material
loops, and fixed point solves size themselves from that count. This lets a MultiApp give many
threads to a sub-app that scales well with them, such as one wrapping OpenMC, while the remaining
apps stay on fewer. The parameter only caps downward: `--n-threads` is the maximum and sets the
OpenMP thread count, and an app requesting more than that is warned and clamped. Ray tracing now
errors unless the two counts match, because its per-thread data structures are always sized to the
process-wide count, so a smaller app count would leave ray tracing threads with no storage.
([idaholab/moose#31489](https://github.com/idaholab/moose/pull/31489))

### AD seeding is now scoped to what consumes it

Automatic differentiation is no longer seeded on data that no object in the input reads:

- `ADIntegratedBC` requested AD for the whole element solution, so AD was seeded on element
  interiors even for an input whose AD consumers are all on faces. MOOSE now tracks whether a
  variable's AD consumers are face-only and, when they are, scopes the AD solution request to
  faces. Computed values are unchanged.
  ([idaholab/moose#33852](https://github.com/idaholab/moose/pull/33852))
- AD mortar face reinitialization on a displaced mesh computed AD shape function gradients and AD
  primal gradients at every mortar quadrature point even when the constraint used neither.
  Mechanical mortar contact uses only values and normals, so those constraints now opt out, and
  `Assembly::computeADFace` computes AD face shape function gradients only once a variable has
  requested them. Other `ADMortarConstraint` subclasses keep their previous behavior, and results
  are unchanged.
  ([idaholab/moose#33959](https://github.com/idaholab/moose/pull/33959))

### Automatic contact pairing supports distributed meshes and recover

`ContactPairLowerDBlockGenerator` is renamed [AutomaticContactPairingGenerator.md] and is now the
only place contact pairs are detected, for every contact formulation. The generator stores the
pairs as mesh meta-data, which [ContactAction.md] reads instead of repeating the search at
`post_mesh_prepared`. Because meta-data is restored from a checkpoint, the pairs survive
`--recover`, where the mesh is already distributed when the action runs. The search itself is now
parallel-safe: `CENTROID` pairing reduces per-boundary area and centroid sums across processes, and
`NODE` pairing gathers owned boundary nodes onto every process before building its k-d tree. The
generator gained a `create_lower_d_blocks` parameter so the pair search can be used without
creating lower-dimensional blocks. Automatic pairing previously failed with `-p2
--distributed-mesh --recover`.

Automatic pairing now requires a mesh built by mesh generators, because the action appends the
generator to the mesh generator tree. An input using a plain `[Mesh] file = ...` gets an error
directing it to [FileMeshGenerator.md].
([idaholab/moose#33979](https://github.com/idaholab/moose/pull/33979))

### MFEM backend improvements

#### Multiple equation systems per problem

An [MFEMProblem.md] can now set up several `EquationSystems` instead of one, matching what
libMesh-based MOOSE problems can already do with multiple nonlinear systems. Weak forms are
declared through the new [MFEMWeakForm.md] family ([MFEMComplexWeakForm.md],
[MFEMEigenproblemWeakForm.md], and [MFEMTimeDependentWeakForm.md]) and attached with
[AddMFEMWeakFormAction.md], [SetMFEMEquationSystemsAction.md], and
[SetMFEMProblemOperatorsAction.md]. This is aimed at block preconditioners, whose blocks may be
formed from deliberately simplified equation system operators.
([idaholab/moose#33492](https://github.com/idaholab/moose/pull/33492))

#### Solver and preconditioner setup

All MFEM solvers now set up their preconditioners the same way and at the same stage, driven by
`LinearSolverBase::SetOperator()` rather than at construction time. The old arrangement forced
stub wrappers for solvers such as `MatrixFreeAMS`, precluded preconditioners such as
`OperatorChebyshevSmoother` entirely, and set the preconditioner a second time for LOR-capable
solvers whether or not LOR was enabled.
([idaholab/moose#34028](https://github.com/idaholab/moose/pull/34028))

#### Multi-threading

`MFEMProblem`-driven apps can now run with `--n-threads` greater than one without workarounds.
`MFEMProblem::addObject()` and `MFEMProblem::addFunction()` add only one object regardless of the
thread count, so identical objects are no longer added once per thread to the coefficient manager.
Although MFEM itself is not currently built with OpenMP, dependencies such as hypre are when GPU
support is off.
([idaholab/moose#33935](https://github.com/idaholab/moose/pull/33935))

MFEM device configuration is now guaranteed to happen exactly once, even when a libMesh app spawns
several MFEM apps, which was not previously possible. Sampler postprocessors initialize their
coordinate vectors in `MFEMSamplerBase::initialSetup()`, so the point coordinates are listed in
outputs that occur before any postprocessor executes.
([idaholab/moose#33741](https://github.com/idaholab/moose/pull/33741))

#### New auxiliary kernels

- [MFEMMeridionalCurlAux.md] computes the cylindrical-coordinate curl of an azimuthal vector
  potential, giving `B_r = -dA_theta/dz` and `B_z = dA_theta/dr + A_theta/r`. The Cartesian 2D curl
  omits the `A_theta/r` term, so axisymmetric magnetostatic formulations that solve for `A_theta`
  could not recover the magnetic flux density before.
  ([idaholab/moose#33655](https://github.com/idaholab/moose/pull/33655))
- [MFEMVectorProjectionAux.md] and [MFEMComplexVectorProjectionAux.md] gained a `coefficient`
  parameter that scales the projected vector coefficient by a scalar coefficient, which is useful
  for field normalizations and for visualizing auxiliary fields.
  ([idaholab/moose#33654](https://github.com/idaholab/moose/pull/33654))

#### Diagnostics and timing

An MFEM object restricted to a block or boundary name that the mesh does not have now reports a
MOOSE input error naming the unknown name or ID, instead of aborting inside
`mfem::AttributeSets::GetAttributeSet`.
([idaholab/moose#34203](https://github.com/idaholab/moose/pull/34203))

MFEM problem operators derive from `PerfGraphInterface` and time forming the system separately
from solving it, so an MFEM run is no longer a single opaque `MooseApp::executeExecutioner`
section. The assembly cost previously had to be inferred by subtracting a solver's own printed
timers from the executioner total, and could not be obtained at all for a solver that prints none.
([idaholab/moose#33844](https://github.com/idaholab/moose/pull/33844))

A curl-curl element matrix was sized incorrectly rather than as the number of DOFs squared,
tripping an MFEM assertion.
([idaholab/moose#34151](https://github.com/idaholab/moose/pull/34151))

### Kokkos backend

- Kokkos systems now support `automatic_scaling = true`. The Jacobian is assembled into the
  libMesh system matrix, which is cast to a `PetscMatrix` so the diagonal or absolute row sum can
  be extracted into the scaling matrix.
  ([idaholab/moose#33867](https://github.com/idaholab/moose/pull/33867))
- Kokkos system setup no longer loops over every MPI rank with one scatter per rank when building
  the DOF maps for overlapping DOFs; it sends to actual neighbors with
  `TIMPI::push_parallel_vector_data`. This removes half of the setup cost observed on large weak
  scaling runs on Frontier and Aurora.
  ([idaholab/moose#33937](https://github.com/idaholab/moose/pull/33937))
- Mixing regular and Kokkos residual objects no longer crashes. COO preallocation wiped out matrix
  options including `MAT_KEEP_NONZERO_PATTERN`, which showed up when regular nodal BCs were mixed
  with Kokkos kernels; the options are now re-applied afterwards.
  ([idaholab/moose#33954](https://github.com/idaholab/moose/pull/33954))
- CUDA is now initialized before MPI. OpenMPI requires this to initialize its `smcuda` byte
  transfer layer, the component that carries shared-memory RDMA transfers between GPUs, so NVLink
  was silently falling back to PCI. On a Griffin run, processor communication dropped from 2.03 s
  to 0.015 s.
  ([idaholab/moose#33585](https://github.com/idaholab/moose/pull/33585))
- A collection of Kokkos fixes landed: forwarding in the object-adding APIs, default coupled
  gradient and nodal value access, missing hooks in Kokkos functions, sideset ID caching in the
  Kokkos mesh, an element with the same sideset on several sides, derivative material APIs, and a
  segfault when finalizing an empty Kokkos jagged array.
  ([idaholab/moose#33985](https://github.com/idaholab/moose/pull/33985))

### Mesh generation and partitioning

- [AdvancedExtruderGenerator.md] gained [!param](/Mesh/AdvancedExtruderGenerator/side_boundary),
  which collects the lateral surface formed by extruding the exterior sides of the input mesh into
  a named boundary, as both a sideset and a nodeset. The top and bottom boundaries already had
  parameters; this covers the last one.
  ([idaholab/moose#34095](https://github.com/idaholab/moose/pull/34095))
- [PetscExternalPartitioner.md] now handles meshes whose dual graph contains edges that are not
  face neighbors. libMesh adds such edges for lower-dimensional elements sitting on a block, for
  the node elements constraining spline DOFs on IsoGeometric Analysis meshes, and for the active
  children of a refined neighbor. The partitioner assumed every edge was a face neighbor and
  stopped with `Cannot construct dual graph correctly since the number of neighbors is
  inconsistent`, and assigned side weights by position, which placed them on the wrong edges. It
  now checks across all processes whether the mesh has any such edges and matches weights to
  edges.
  ([idaholab/moose#34050](https://github.com/idaholab/moose/pull/34050))
- `PetscExternalPartitioner` also no longer crashes inside PTScotch when element or side weights
  are used and a rank's partition is empty, which happened with more ranks than elements and
  produced a confusing error from the third-party library.
  ([idaholab/moose#33836](https://github.com/idaholab/moose/pull/33836))

### Input and parameter error reporting

- A missing required parameter is now reported before other parameter errors. Previously a private
  or unused parameter error could be reported first, hiding the actual fix from the user; the
  example in the originating issue was `ParsedGenerateNodeset` reporting a private-parameter error
  rather than the missing `new_nodeset_name`.
  ([idaholab/moose#33196](https://github.com/idaholab/moose/pull/33196))
- `MooseUtils::tokenizeAndConvert` can now throw when a token fails to convert, rather than only
  returning failure. It throws `std::invalid_argument` directly, because `MooseError.h` cannot be
  included from the header-only `MooseStringUtils.h` that the capabilities Python module uses.
  ([idaholab/moose#33943](https://github.com/idaholab/moose/pull/33943))
- The `index`/`component` parameters of [MaterialRealDenseMatrixAux.md],
  `MaterialStdVectorRealAux`, and their relatives are now required instead of defaulting to 0. A
  user working with array material properties would reasonably expect the whole vector to be
  output, and the silent default gave them one component with no indication.
  ([idaholab/moose#33806](https://github.com/idaholab/moose/pull/33806))
- [ArrayDiffusion.md], [ArrayReaction.md], `ArrayTimeDerivative`, `ADArrayReaction`, and
  `ArrayDGDiffusion` now check once in `initialSetup()` that each array material property
  coefficient has one entry per array variable component, so optimized builds error instead of
  reading out of bounds. The check uses `VariableSizeMaterialPropertiesInterface`, which
  [GenericConstantArray.md] and `GenericConstant2DArray` now implement, and which gained
  `getMatrixPropertySize()` for matrix coefficients.
  ([idaholab/moose#33891](https://github.com/idaholab/moose/pull/33891))
- Reactor geometry mesh builder parameter checks that were previously skipped under `--csg-only`
  now run, because the skippable sub-generators that carried them are no longer the only place
  they happen.
  ([idaholab/moose#34140](https://github.com/idaholab/moose/pull/34140))

### Preconditioning and solver setup

A user-specified `SMP` block previously defaulted to `full = false`, so adding a
[Preconditioning](syntax/Preconditioning/index.md) block to a `NEWTON` input silently dropped the
off-diagonal Jacobian blocks that the automatically created preconditioner includes. `SMP` now
defaults to full coupling for `NEWTON` and `LINEAR` solves unless `full`,
`off_diag_row`/`off_diag_column`, or `coupled_groups` is specified. The automatic preconditioner is
also created for each nonlinear system that does not have one in the `[Preconditioning]` block,
rather than being disabled for every system as soon as the block exists.
([idaholab/moose#34036](https://github.com/idaholab/moose/pull/34036))

The kernel coverage check is now restricted, for each nonlinear system, to the intersection of the
blocks the `Problem` selects and the blocks holding field variables of that system. It previously
required every system to have a kernel on every Problem-selected block, so valid multi-system
inputs with block-restricted variables had to disable `kernel_coverage_check` entirely. An
unrestricted field variable still requires coverage on all Problem-selected blocks.
([idaholab/moose#33919](https://github.com/idaholab/moose/pull/33919))

### Interface kernels across h-refinement

Interface kernels now contribute on a sideset whose coarse side faces refined elements. The coarse
element's neighbor across the sideset is an inactive ancestor once it is cut into finer elements,
so the whole face was silently skipped. The coarse side is now assembled against each active child
of that ancestor in turn, with element weights adjusted for the refinement, and auxiliary variables
are reinitialized on the mismatched faces as well. This matters because which side of such a
boundary is refined is not always under the user's control.
([idaholab/moose#33963](https://github.com/idaholab/moose/pull/33963))

### CSV files with mixed data types

Objects that read CSV data through `DelimitedFileReaderTempl` required every entry in a column to
share one type across the whole file. The new `MixedDataDelimitedFileReader` reads the file as
strings and converts only the requested column to the requested type, so a file with columns of
differing types can be used when only some of them are needed.
[CSVTimeSequenceStepper.md] is the first consumer.
([idaholab/moose#34062](https://github.com/idaholab/moose/pull/34062))

### AI-assisted development

`AGENTS.md` now requires a `PetscJacobianTester` test for every hand-coded Jacobian change,
covering each coupling and coordinate system the change affects, because a correct residual does
not imply a correct Jacobian and only a finite-difference comparison catches a missing or wrong
term. The `write-regression-tests` skill gained a reference on what such a test must exercise and
how to distinguish a wrong Jacobian from finite-difference noise, and a new `issue-create` skill
drafts issues following the repository's templates.
([idaholab/moose#34091](https://github.com/idaholab/moose/pull/34091))

`scripts/civet_pr_failures.py` reports why CIVET CI failed on a pull request: which jobs really
failed, the build errors or failing tests inside them, a clustering of error signatures, and a
reproduce command taken from the invocation each step logged. It reads GitHub commit statuses and
CIVET job logs through the `gh` CLI, so it needs no CIVET credentials. The accompanying
`civet-ci-failures` skill documents how to read the report, because raw job counts and GitHub's own
rollup state both mislead: dependency cascades present as failures, the combined state turns to
failure on the first failing job, a starting event looks finished, and a job CIVET records as
allowed-to-fail arrives as success.
([idaholab/moose#33756](https://github.com/idaholab/moose/pull/33756))

An `update-packages` skill covering the monthly distributed-package update was added alongside this
month's package bump, and the CodeGraph configuration now lists `*.C`, `*.h`, and `*.K` as C++
extensions, which it did not previously treat as such.
([idaholab/moose#33833](https://github.com/idaholab/moose/pull/33833),
[idaholab/moose#33879](https://github.com/idaholab/moose/pull/33879))

### TestHarness

- On Linux, test memory is now measured as `Pss - Pss_File`, excluding file-backed pages. Measuring
  plain `Pss` split the executable and library pages shared by every running test across however
  many tests happened to be running, so a test running alone was charged nearly all of them and
  small tests such as `mortar/continuity-3d-non-conforming` were intermittently killed with "OVER
  MEMORY" on CIVET. The measurement is chosen once at startup by kernel: `Pss - Pss_File` on Linux
  5.3 and newer, plain `Pss` on Linux 4.14 through 5.2 where `smaps_rollup` lacks `Pss_File`, and
  RSS elsewhere. Both `Pss` measurements stay proportional, so memory shared by a test's MPI ranks
  is split across them. `RESULTS_VERSION` is bumped to 10. Measured against per-step peaks from a
  CIVET event, 55 `min_slots` entries this made necessary were removed and 5 more reduced from 3 to
  2, keeping the 25 with less headroom. The memory monitor also samples at the requested period
  rather than one that grows with the length of a pass, publishes each pass's samples in one step
  so a read between clearing and refilling cannot miss a running test, and shuts down its `Manager`
  process on `stop()`.
  ([idaholab/moose#34075](https://github.com/idaholab/moose/pull/34075))
- Output that cannot be decoded as UTF-8 no longer fails a test or drops the stream it came from.
  The bytes are kept as backslash escapes and the test gets an "invalid UTF-8 in output" caveat, so
  its result comes from its own checks.
  ([idaholab/moose#34112](https://github.com/idaholab/moose/pull/34112))
- `SchemaDiff` compared string lists containing negative values incorrectly, carrying the same sign
  errors that were fixed for scalars in #33304. Two values now count as zero only when both
  `abs(x)` and `abs(y)` fall below `abs_zero`, where before any two negative values passed; the
  relative error divides by `abs(y)`, where before a negative `y` made it negative so it never
  exceeded `rel_err` and `"1 -2"` compared equal to `"1 -2.5"`; and a pair below `abs_zero`
  continues to the next element instead of returning, where before the rest of the list was
  skipped so `"1e-11 1"` compared equal to `"2e-11 2"`.
  ([idaholab/moose#33980](https://github.com/idaholab/moose/pull/33980))

## MOOSE Bug Fixes

### Jacobian correctness

- `ADScalarKernel` passed the residuals of every component of a scalar variable to `addJacobian`
  in one call, but `Assembly::cacheJacobian` requires all rows of such a call to depend on the
  same degrees of freedom, which the components of a higher-order scalar variable need not:
  component `i` of [ADScalarTimeDerivative.md] depends only on DOF `i`. Optimized builds dropped
  the Jacobian entries of the later components, so a `SECOND` order variable lost its second row
  and the Jacobian was singular, while debug builds stopped on a `mooseAssert`. Each component is
  now added separately, at no extra cost to other AD objects.
  ([idaholab/moose#33967](https://github.com/idaholab/moose/pull/33967))
- `ComputeNodalKernelJacobiansThread::onNode` collected an active `NodalKernel` once per block of
  the node it was active on, so its Jacobian was added several times on nodes shared by
  subdomains, including the nodes of lower-dimensional blocks. The residual thread already
  executes each nodal kernel once on such nodes, so the Jacobian did not match the residual and
  Newton lost quadratic convergence. The Jacobian thread now skips nodal kernels it has already
  collected for a node and coupled variable. Results are unchanged elsewhere.
  ([idaholab/moose#33972](https://github.com/idaholab/moose/pull/33972))
- The AD overloads of `Assembly::cacheResiduals` and `Assembly::cacheJacobian` skipped libMesh
  constraint application whenever a single residual was added, assuming such calls come from
  finite volume objects. If that DOF was constrained by a periodic boundary condition, a hanging
  node, or another `DofMap` constraint, libMesh later overwrote the constrained row and the
  contribution was silently lost rather than distributed to the constraining DOFs. The shortcut is
  now taken only when the DOF is unconstrained, so finite volume assembly is unaffected. This
  affects every object adding one AD residual at a time on a constrained DOF, such as
  `ADNodalKernel` and mortar constraints with single-DOF lower-dimensional elements. `ADNodalBC`
  Jacobian rows are excluded: a nodal BC replaces its own row, so distributing a Dirichlet row on a
  hanging node would zero the rows of its parent DOFs and leave the Jacobian singular.
  ([idaholab/moose#33969](https://github.com/idaholab/moose/pull/33969))
- `JvarMapInterface` indexed variables of other solver systems the same way as current-system
  ones, rather than from the top down as it does for auxiliary variables, so kernels relying on
  the jvar map, such as those in solid mechanics and phase field, formed an inexact Jacobian under
  multi-system solves.
  ([idaholab/moose#33977](https://github.com/idaholab/moose/pull/33977))
- `MooseVariableDataBase<RealEigenVector>::fetchDofValues()` read an array variable's second time
  derivative from `solutionUDot()`, the first-derivative vector, so `coupledArrayDotDot()` returned
  the first time derivative. It now reads `solutionUDotDot()`. This affects array variables under a
  second-order time integrator such as `NewmarkBeta`.
  ([idaholab/moose#34107](https://github.com/idaholab/moose/pull/34107))

### Exception handling and timestep rejection

- A user object throwing on only some MPI ranks hung the simulation: the ranks that threw went
  straight to the exception handler, which communicates, while the others waited in a user
  object's `finalize()` communication, and neither side could proceed. This affected element,
  side, nodal, mortar, and general user objects alike. Each stage of work in
  `FEProblemBase::computeUserObjectsInternal` now catches its own exceptions and records them
  without communicating, and every rank reaches one `checkExceptionAndStopSolve()` before that
  stage's `finalize()` calls. That method throws the new `MooseHandledException`, which the
  enclosing residual and Jacobian handlers rethrow untouched, so an exception already communicated
  during a residual or Jacobian evaluation is no longer wrapped twice and the solve is stopped
  once.
  ([idaholab/moose#33909](https://github.com/idaholab/moose/pull/33909))
- A non-finite displaced mesh coordinate, for instance after a failed linear solve, now throws a
  `MooseException` in `DisplacedProblem::updateMesh`, so the time step is cut rather than the run
  aborting later inside mortar generation.
  ([idaholab/moose#34035](https://github.com/idaholab/moose/pull/34035))
- A [Terminator.md] user object in a soft-fail mode left the fixed point status unset, so a
  transient with fixed point iterations hit `Internal error: wrong fixed point status!` instead of
  failing the step and reducing the time step size.
  ([idaholab/moose#33962](https://github.com/idaholab/moose/pull/33962))
- `XFEM` now records the timestep at which crack-growth marks are added and discards marks from the
  current timestep at the start of `XFEM::update()`. Valid marks always come from the previous
  timestep, so the only marks dropped are those left by a rejected attempt. This also fixes
  `crack_propagation_var`, whose failure was hidden because it was a dependent of another test.
  ([idaholab/moose#34004](https://github.com/idaholab/moose/pull/34004))
- `--test-restep` fails one timestep on purpose to check that a rejected step leaves no stale
  state, but with `Executioner/abort_on_solve_fail = true` that forced failure ended the run, so
  such tests had to opt out of restep testing. `TransientBase::keepGoing()` no longer aborts on
  the failure `--test-restep` forces. Any other failed solve still aborts when the flag is set, in
  normal and restep runs alike.
  ([idaholab/moose#33999](https://github.com/idaholab/moose/pull/33999))

### Contact and mortar fixes

- Penalty mortar contact lost its history across `--recover`. `formulation = mortar_penalty`
  carries tangential traction and slip history for friction, plus augmented Lagrange (AL)
  multipliers, from one time step to the next, and [PenaltyFrictionUserObject.md] and
  [PenaltyWeightedGapUserObject.md] kept this state in maps keyed by `const DofObject *`, which
  cannot be checkpointed. A recovered run therefore continued from zero friction history and zero
  multipliers, with no error, and gave contact forces differing by 0.6% to 2.8% in the reported
  reproducer. The maps are now keyed by node ID and declared as restartable data, as
  `CohesiveZoneModelBase` already does for its own history.
  ([idaholab/moose#34128](https://github.com/idaholab/moose/pull/34128))
- `PenaltyWeightedGapUserObject` and `PenaltyFrictionUserObject` now save their augmented Lagrange
  state at the start of each timestep and restore it when the step is retried.
  ([idaholab/moose#34001](https://github.com/idaholab/moose/pull/34001))
- The AL update of a slipping node set its total tangential traction to
  `penalty_friction * |normal_lm|` instead of the Coulomb cone value `mu * |normal_lm|`. With a
  typical friction penalty the multiplier was off by many orders of magnitude, about 1e12 rather
  than a few thousand in `cylinder_friction_penalty_frictional_al.i`, so the AL loop did not
  converge to the Coulomb solution at slipping nodes. Frictional AL results change.
  ([idaholab/moose#34100](https://github.com/idaholab/moose/pull/34100))
- `AugmentedLagrangianContactConvergence` now passes its incremented iteration count back to the
  problem, so `maximum_lagrangian_update_iterations`, node-face `penalty_multiplier` growth, and
  `NumAugmentedLagrangeIterations` all see the real count. Existing golds are unchanged.
  ([idaholab/moose#34038](https://github.com/idaholab/moose/pull/34038))
- The quasi-static mortar friction constraint passed a sliding speed of zero to
  `function_friction`, so speed-dependent friction had no effect. The sliding speed at each node is
  now the weighted tangential velocity divided by the integral of the node's test function, the
  mortar-projected nodal slip rate of Wohlmuth (2011, Acta Numerica, eq. 3.10a). Constant and
  pressure-only friction are unchanged. The weighted-displacement accumulation also moves from
  `WeightedGapUserObject` into `CohesiveZoneModelBase`, its only user, so other contact models no
  longer build it.
  ([idaholab/moose#34016](https://github.com/idaholab/moose/pull/34016))
- Dynamic mortar contact passed a sliding speed several times too large to a speed-dependent
  friction law, which could drive the friction coefficient negative. It now uses the same
  quantity as the quasi-static constraint: the weighted relative velocity divided by the node's
  weight. A constant `mu` must now be positive, and inputs with `mu <= 0` error. Results change
  only for dynamic mortar contact with `function_friction`; in the regolded test the friction
  coefficient goes from about -0.48 to 0.48.
  ([idaholab/moose#34020](https://github.com/idaholab/moose/pull/34020))
- The 3D mortar nearest-neighbor search, which finds the primary-surface elements facing each
  secondary element, only examined node IDs below the mesh's node count. Node IDs are not always
  contiguous: combining or deleting parts of meshes with `allow_renumbering = false` leaves gaps.
  Primary nodes with IDs above the node count were never found and the mortar segments depending on
  them were dropped with only a warning, which in a mechanical contact problem could switch contact
  off across the whole interface so the blocks passed through each other while the solve still
  converged. The k-d tree adaptor now covers every node ID below `max_node_id()`.
  ([idaholab/moose#34031](https://github.com/idaholab/moose/pull/34031))
- Only the owner of an inactive secondary node zeroes its Lagrange multiplier DOFs, but
  `AutomaticMortarGeneration` shared the inactive set only with ranks holding a secondary element
  touching the node. An owner holding none left the node's LM rows empty, so LU hit a zero pivot
  and the run aborted on a NaN mesh; `bouncing-block-contact.split_secondary` failed this way at
  3, 6, 7, and 8 ranks. Each rank now sends its local data straight to the node owners in one
  round of communication.
  ([idaholab/moose#34033](https://github.com/idaholab/moose/pull/34033))
- `AutomaticMortarGeneration::computeMsmStatistics` segfaulted on a mortar interface where no
  mortar segments form, which is exactly the case `debug_mesh = true` and
  `MortarSegmentMeshReporter` exist to diagnose. It called libMesh's `StatisticsVector::maximum()`
  and `minimum()` on empty volume lists, dereferencing the `end()` iterator. Both now report 0 for
  an empty list, matching `StatisticsVector::median()`.
  ([idaholab/moose#34174](https://github.com/idaholab/moose/pull/34174))
- [MortarUserObjectAux.md] checked the wrong user object type before reading `active_set` and
  `delta_tangential_lm_one`/`two`. The active set could not be output for frictionless penalty
  contact, giving a spurious input error, and requesting these quantities from a Lagrange
  multiplier friction user object segfaulted instead of giving an input error. The checks now use
  the classes that provide the values, and `PenaltyWeightedGapUserObject::getActiveSetState`
  returns `false` for a node absent from its map rather than reading past the end of it.
  ([idaholab/moose#34139](https://github.com/idaholab/moose/pull/34139))
- [MortarGenericTraction.md] segfaulted at the first residual when `use_displaced_mesh = true` was
  omitted from its block. The cohesive zone user object it reads traction from always runs on the
  displaced mesh, and mortar user objects are only reinitialized for constraints on the same mesh,
  so the default `use_displaced_mesh = false` left it reading an empty traction array. The
  parameter now defaults to `true`, and setting it to `false` is an input error. No input changes:
  every existing block already sets it, and that line can now be omitted.
  ([idaholab/moose#34144](https://github.com/idaholab/moose/pull/34144))
- `Assembly::reinitDual()` no longer recomputes custom dual coefficients for lower-dimensional FE
  types that never requested dual shape data. On second-order meshes `_fe_lower` also holds the
  geometric helper FE, so a mixed-order mortar discretization with a first-order dual Lagrange
  multiplier could try to factor an unused second-order Gram matrix over a restricted covered
  region, and libMesh threw before assembling the requested first-order basis if that matrix was
  singular or numerically non-positive-definite.
  ([idaholab/moose#33907](https://github.com/idaholab/moose/pull/33907))
- `CohesiveZoneModelBase` built the primary-side displacement gradients with `adCoupledGradient`,
  so the interface deformation gradient used only the secondary side. It now uses
  `adCoupledNeighborGradient`, pads the gradient vectors to three components, and checks the
  primary-side deformation gradient for non-finite values. Results change for mortar cohesive zone
  models wherever the deformation differs across the interface.
  ([idaholab/moose#34009](https://github.com/idaholab/moose/pull/34009))
- Creating a displaced mesh on a mesh with disjoint neighbor boundary pairs is now an input error.
  `BreakMeshByBlockGenerator` connects the elements on the two sides of a cut as disjoint
  neighbors, which libMesh finds by matching the positions of their sides. On a displaced mesh the
  sides move apart once the cut opens, so anything rebuilding neighbor links afterwards, such as
  the Exodus gather of a distributed mesh or `--recover`, failed with
  `Periodic boundary neighbor not found`. `SetupMeshCompleteAction` now reports a `paramError` on
  `displacements` pointing to `use_displaced_mesh = false` with the Lagrangian solid mechanics
  kernels, or to the mortar cohesive zone model.
  ([idaholab/moose#34042](https://github.com/idaholab/moose/pull/34042))
- `lag_displacement_jump` on [BilinearMixedModeCohesiveZoneModel.md] is deprecated. It was
  declared but never read, so `true` and `false` always gave identical results. Lagging the jump
  would make the damage update explicit, overshooting the peak traction past the strength and
  making the dissipated energy depend on the time step with no way to control that error; the
  mortar CZM already has `viscosity`, which converges to the rate-independent model as the
  viscosity goes to zero, and the model is AD, so lagging offers no Jacobian benefit either.
  ([idaholab/moose#34134](https://github.com/idaholab/moose/pull/34134))

### Miscellaneous

- [MOOSEQuantityToNEML2.md] read `VARIABLE` inputs through
  `FEProblemBase::getStandardVariable(...).sln()` without ever calling
  `addMooseVariableDependency`. When another user object in the same loop declared a variable
  dependency, for example an `ElementAverageValue` postprocessor executing on `LINEAR`,
  `ComputeUserObjectsThread` reinitialized only the declared variables, so the NEML2 input
  variable was left stale or zero. It now declares its dependency.
  ([idaholab/moose#34187](https://github.com/idaholab/moose/pull/34187))
- `DMSetUp_Moose` registered `SNESFunction_DMMoose` and `SNESJacobian_DMMoose` on the top-level
  `DMMoose`, but `PetscNonlinearSolver::solve()` calls `SNESSetFunction` and `SNESSetJacobian`
  after `FieldSplitPreconditioner::setupDM()` attaches that DM, registering libMesh's callbacks on
  the same DM through the same `DMSNES` entry points. The `DMMoose` callbacks were therefore
  replaced before PETSc could call them, and are now removed along with `DMMooseFunction`,
  `DMMooseJacobian`, and the unregistered `SNESUpdateDMMoose`. `DMVariableBounds_Moose` stays,
  because libMesh sets no variable bounds of its own.
  ([idaholab/moose#34093](https://github.com/idaholab/moose/pull/34093))
- IsoGeometric Analysis initial conditions are now projected rather than interpolated where spline
  nodes should not be evaluated directly. Interpolated initial conditions are less accurate on
  body-fit meshes and potentially unusable on flex meshes. Some gold solutions change. The non-IGA
  path gains one parallel reduction, to confirm that every rank agrees the mesh is not IGA.
  ([idaholab/moose#34055](https://github.com/idaholab/moose/pull/34055))
- Regression tests no longer depend on console coloring, which `--no-color` can switch off; the
  behavior is covered by a unit test instead.
  ([idaholab/moose#33476](https://github.com/idaholab/moose/pull/33476))
- `PetscJacobianTester` judges a Jacobian by the relative measure
  `||J - Jfd||_F / ||J||_F < ratio_tol` alone, because `difference_tol` now defaults to infinity.
  The absolute difference scales with the magnitude of the Jacobian entries, so the old default of
  `1` failed correct Jacobians on finite-difference noise whenever the entries were large. The
  parameter remains for specs wanting an absolute check, and specs that set it keep their value.
  The tester documentation listed both defaults as `1e-8` and is corrected.
  ([idaholab/moose#33976](https://github.com/idaholab/moose/pull/33976))
- The Python precheck script added earlier in the month was removed again, leaving the repository
  without `scripts/pre_check.py`. The unused Cosserat theory figure files that the same change
  deleted stay deleted.
  ([idaholab/moose#31527](https://github.com/idaholab/moose/pull/31527),
  [idaholab/moose#34214](https://github.com/idaholab/moose/pull/34214))
- Apps without a Console output (e.g. `[Outputs] console = false`) no longer keep every message
  written to `_console` in memory. The buffer was never cleared and was copied at every flush, so
  long-running (sub-)apps, such as a MultiApp running many solves in one process, grew slower as
  the number of messages increased.
  ([idaholab/moose#34118](https://github.com/idaholab/moose/issues/34118))

## MOOSE Modules Changes

### Contact module

Mechanical mortar contact now assembles the contact force by interpolating the nodal traction
vector with the traction basis, instead of scaling an interpolated scalar pressure by the nodal
normal of the residual row's own node. Only the former is the transpose of the weighted gap, so the
contact force is now self-equilibrated across the interface and no longer depends on secondary node
numbering. Contact forces and converged results therefore change on interfaces where the secondary
nodal normals vary along the face.

Local-basis quasistatic `mortar` and `mortar_penalty` contact Jacobians now also include
derivatives of the averaged secondary nodal normals and their tangent basis. These derivatives can
require a larger AD container on high-order or high-valence interfaces. Because the contact
coupling changes during the solve in most contact problems, such as when surfaces slide or come into
contact, set `Problem/use_hash_table_matrix_assembly = true` to accommodate the changing sparsity
pattern.
([idaholab/moose#33390](https://github.com/idaholab/moose/pull/33390))

### Solid Mechanics module

- New [SecondDerivativeRegularization.md] and `ADSecondDerivativeRegularization` kernels add a
  regularization term built from second derivatives of a scalar variable, selected with
  `regularization = huhu`, `lulu`, or `huhu_lulu` and scaled by a required `coefficient`
  (`huhu_lulu` also takes `lulu_factor`). The motivating terminology comes from HuHu/LuLu
  regularization in third-medium contact, but the kernels are general; for a vector field, add one
  per component. The kernels evaluate second derivatives of the trial and test functions, so the
  FE family and order must be one for which libMesh provides meaningful second derivatives.
  ([idaholab/moose#32974](https://github.com/idaholab/moose/pull/32974))
- The `BiLinearMixedModeTraction` cohesive zone material model recovered the wrong Mode II fracture energy and had an inconsistent
  hand-coded Jacobian. The pure Mode II final separation carried an extra factor of `sqrt(2)`,
  `delta_f = 2*sqrt(2)*GIIc/S` rather than the `delta_f = 2*GIIc/S` that energy consistency
  requires for the bilinear traction-separation law, so the area under the Mode II curve did not
  recover the prescribed `GIIc`. Both issues are fixed, and cohesive zone results change.
  ([idaholab/moose#33902](https://github.com/idaholab/moose/pull/33902))

### Porous Flow module

- New [TabulatedPVTFluidProperties.md] reads PVDO/PVDG-style black-oil PVT data: a density at
  standard conditions, and a table of pressure, formation volume factor B, and viscosity. Following
  black-oil simulator convention, `1/B` and `1/(B*mu)` are interpolated linearly in pressure, and
  `rho = rho_sc/B` with `mu = (1/B)/(1/(B*mu))`, giving exact pressure derivatives. Outside the
  table, `out_of_bounds_behavior` selects linear extrapolation, throwing so the time step is cut,
  or clamping to the end values. The table is isothermal. Dead oil plus water is a two-component,
  two-phase problem that existing PorousFlow machinery already handles, so this is the first step
  toward a black-oil capability.
  ([idaholab/moose#34113](https://github.com/idaholab/moose/pull/34113))
- New [PorousFlowPorosityVinsomeWesterveld.md] captures the thermal opening of a lower-dimensional
  fracture as cold injection cools and contracts the adjacent rock. It derives from
  [PorousFlowPorosityLinear.md] and subtracts `thermal_opening_coeff * I`, where `I` is the heat
  content of the adjacent matrix computed by the semi-analytic method of Vinsome and Westerveld
  (1980) and stored as stateful material properties. Because `I` is linear in the current
  temperature, the Jacobian is exact. The cooled layer is normally much thinner than a matrix
  element, so it is not resolved by the mesh, which is what makes the semi-analytic treatment
  necessary.
  ([idaholab/moose#34049](https://github.com/idaholab/moose/pull/34049))
- `porosity_min` moved into `PorousFlowPorosityBase`, so every porosity Material can enforce a
  lower bound rather than only [PorousFlowPorosityLinear.md] and `PorousFlowPorosityExponentialBase`,
  which each carried their own copy. It is an optional range-checked parameter: if unset nothing
  happens, and if set, the floor is applied through a common `applyPorosityMin()` for both AD and
  non-AD, with derivatives multiplied by `zero_modifier` where it is active.
  ([idaholab/moose#33950](https://github.com/idaholab/moose/pull/33950))
- [PorousFlowBrineCO2.md], [PorousFlowWaterNCG.md], and the other `PorousFlowFluidState` user
  objects gained `compute_enthalpy` and `compute_internal_energy` flags, matching
  `PorousFlowSingleComponentFluid`. Profiling found a case spending 26% of its time computing
  enthalpy and internal energy for an isothermal model that never used either.
  ([idaholab/moose#33349](https://github.com/idaholab/moose/pull/33349))
- The volumetric strain kernels and materials are now templated for AD:
  [PorousFlowMassVolumetricExpansion.md], [PorousFlowHeatVolumetricExpansion.md],
  [PorousFlowDesorpedMassVolumetricExpansion.md], [PorousFlowFullySaturatedMassTimeDerivative.md],
  [PorousFlowPorosity.md], and [PorousFlowVolumetricStrain.md]. This continues the work of letting
  the FE kernels use the AD materials the FV kernels already use, rather than requiring hand-coded
  Jacobians.
  ([idaholab/moose#33754](https://github.com/idaholab/moose/pull/33754))
- `PorousFlowDarcyBase` weighted the Darcy flux by the non-AD `_JxW * _coord` in both its AD and
  non-AD flavors. On a displaced mesh with the displacements as variables, the AD weight
  `_ad_JxW * _ad_coord` carries `d(JxW)/d(disp)`, so the displacement block of the Jacobian was
  missing that term for `ADPorousFlowAdvectiveFlux`, `ADPorousFlowHeatAdvection`,
  `ADPorousFlowFullySaturatedAdvectiveFlux`, and `ADPorousFlowFullySaturatedUpwindHeatAdvection`.
  The residual was already correct. The AD flavor now uses the AD weight on a displaced mesh, as
  `ADKernel` does, and keeps the non-AD weight elsewhere, which is the one XFEM rescales.
  ([idaholab/moose#33995](https://github.com/idaholab/moose/pull/33995))
- `PorousFlowDarcyBase::computeResidualAndJacobian` is renamed `computeResidualOrJacobian`. It
  computes one or the other, so the old name was a misnomer that also collided with the framework's
  `computeResidualAndJacobian()` used by the `residual_and_jacobian_together` mechanism.
  ([idaholab/moose#33309](https://github.com/idaholab/moose/pull/33309))
- A git conflict marker committed into `porous_flow.bib` was removed.
  ([idaholab/moose#34054](https://github.com/idaholab/moose/pull/34054))

### Navier-Stokes module

- Conjugate heat transfer interfaces solved with the LinearFV segregated (SIMPLE) solver can now
  include surface-to-surface radiation. Setting
  [!param](/Executioner/SIMPLE/surface_radiation_object_name) to a
  [GrayLambertSurfaceRadiationBase.md] user object, such as
  [ViewFactorObjectSurfaceRadiation.md], adds the net outward radiative heat flux to the energy
  balance on every CHT interface belonging to that object, so the energy equation can be solved
  throughout an enclosure while accounting for radiative exchange at solid-fluid boundaries. The
  user object computes one averaged radiative flux per sideset.
  ([idaholab/moose#33743](https://github.com/idaholab/moose/pull/33743))
- CHT interfaces also gained [!param](/Executioner/SIMPLE/thermal_resistance), an area-normalized
  thermal resistance in m^2*K/W given as one functor for all interfaces or one per interface,
  which enters through an effective wall temperature.
  ([idaholab/moose#33772](https://github.com/idaholab/moose/pull/33772))

### Thermal Hydraulics module

- THM Components can now participate in multi-system solves. `Simulation::addSimVariable()` takes
  an optional solver system name, defaulting to `nl0`, so existing inputs are unaffected.
  ([idaholab/moose#33925](https://github.com/idaholab/moose/pull/33925))
- New scalar kernels add a path-integrated incompressible flow capability:
  [IncompressibleMomentumSPScalarKernel.md] and
  [CoupledPressureIncompressibleMomentumSPScalarKernel.md] integrate 1D momentum along a flow path
  of geometrically varying segments acting on a mass flow rate scalar variable, and
  [IncompressibleEnergySPScalarKernel.md] does the same for energy. This gives THM a simple 1D
  incompressible option, intended among other things as a basis for species transport studies.
  ([idaholab/moose#33692](https://github.com/idaholab/moose/pull/33692))
- Those same kernels fetched coupled scalar variables through the non-AD
  `ScalarCoupleable::coupledScalarVariable` rather than the templated
  `coupledGenericScalarValue<is_ad>`, silently zeroing the off-diagonal Jacobian entries of their
  AD instantiations.
  ([idaholab/moose#34064](https://github.com/idaholab/moose/pull/34064))

### Subchannel module

- The Pacio-Chen-Todreas Detailed model for hexagonal wire-wrapped assemblies is available as the
  SCM closure pair [SCMFrictionChenTodreas.md] and [SCMMixingChenTodreas.md], renamed from the
  Upgraded Cheng-Todreas classes they build on. The model follows the Upgraded Cheng-Todreas
  pressure drop correlation with different parameter and coefficient values, and the module's
  friction verification documentation now compares the available friction factor closures.
  ([idaholab/moose#33634](https://github.com/idaholab/moose/pull/33634))
- Three bugs are fixed in [SCMQuadPowerIC.md], [SCMTriPowerIC.md], [SCMQuadPowerAux.md], and
  [SCMTriPowerAux.md], and their documentation is corrected. An `axial_heat_rate` depending on x or
  y gave pin powers inconsistent with the radial power distribution, because the per-pin correction
  evaluated the function at x = y = 0; it is now evaluated at each pin's nodes, so one function can
  give each pin its own axial shape. Results for z-only shapes are unchanged. The aux kernels also
  applied a time-dependent `power` postprocessor one time step late, having computed pin powers in
  `timestepSetup()` before any postprocessor executes; the setup hooks now compute only the
  power-independent per-pin integral of the axial shape and `computeValue()` scales by the current
  `power`, with a warning if the `power` postprocessor does not execute on all of the aux kernel's
  `execute_on` flags.
  ([idaholab/moose#34083](https://github.com/idaholab/moose/pull/34083))
- The `n_blocks` axial block-marching parameter of `SubChannel1PhaseProblem` now defaults to 1
  instead of being required. Most inputs use a single block, and the remaining multi-block inputs
  can solve over the full axial domain directly.
  ([idaholab/moose#34046](https://github.com/idaholab/moose/pull/34046))
- The SubChannel thermo-mechanical coupling example runs again, conserves the pin power exactly
  where it previously lost 1.4% of it on the way back to SCM, and is now tested in the combined
  module. The `q_prime` transfer preserves the pin surface heat rate, taken from the heat
  conduction residual at the pin surface nodes so it balances the heat source on any mesh, and the
  example gained an optional transfer that interpolates the pin surface temperature linearly
  instead of imposing a piecewise-constant profile. `SubChannel1PhaseProblem` no longer segfaults
  when [SCMPinPowerPostprocessor.md] executes on `initial`, and the SCM postprocessors reading the
  subchannel solution broadcast their value from processor 0, so the example runs in parallel.
  ([idaholab/moose#34155](https://github.com/idaholab/moose/pull/34155))

### Stochastic Tools module

The deep reinforcement learning capability gained parallel sampler gathering and bounded actions,
aimed at autonomous reactor control where signal delay makes ground control impractical, such as
cislunar or lunar microreactors. [LibtorchDRLControl.md] and [LibtorchDRLControlTrainer.md] can
bound the control action so the controller cannot drive the system to a nonphysical state, a new
[SamplerDRLControlTransfer.md] gathers observations across samplers in parallel, and the supporting
`LibtorchObservationHistoryHelper` and `LibtorchRandomUtils` utilities were added to the framework's
libtorch interface.
([idaholab/moose#32802](https://github.com/idaholab/moose/pull/32802))

### Fluid Properties module

- A NaN reaching LAPACK through a Newton solve crashed [TabulatedBicubicFluidProperties.md], seen
  on an Apple M4, where a fluid property evaluated out of range can return NaN in an optimized
  build without the debug-mode check catching it. The Newton inversion now checks `isfinite` on
  the raw value of its AD numbers and `isnan` on the derivatives, and warm-starts its solves when
  a fluid property user object is in use.
  ([idaholab/moose#33921](https://github.com/idaholab/moose/pull/33921))
- [LeadLithiumFluidProperties.md] documentation was clarified. Several readers had misread the
  temperature units: the implemented formula takes Kelvin, while the original source equation was
  written in Celsius. The equation is rewritten to imply Kelvin while keeping a form comparable to
  the source, and a source URL is added.
  ([idaholab/moose#34061](https://github.com/idaholab/moose/pull/34061))

### SQA test documentation coverage

Test specification files in the chemical reactions and porous flow modules that were missing the
`requirement`, `design`, or `issues` fields required by MOOSE's SQA testing convention had them
backfilled, by tracing each test to its originating commit, verifying the referenced issue, and
mapping each test to the documentation page of the objects it exercises.
([idaholab/moose#33930](https://github.com/idaholab/moose/pull/33930),
[idaholab/moose#33934](https://github.com/idaholab/moose/pull/33934))

### Fluid properties module

The new `NASA7IdealGasFluidProperties` describes H2, O2, H2O, CH4, CO, CO2, and N2 as ideal gases
whose heat capacity, enthalpy, and entropy depend on temperature through the NASA 7-coefficient
polynomials of GRI-Mech 3.0. Its enthalpies include the enthalpy of formation, so the energy of a
mixture accounts for the heat of reaction. `IdealGasMixtureFluidProperties` accepts these gases as
components. Viscosity and thermal conductivity are not yet available for them, so they cannot yet
be used in the gas-mixture flow channels of the thermal hydraulics module
([idaholab/moose#34123](https://github.com/idaholab/moose/pull/34123)).

The PETSc submodule was updated from

OpenBLAS is held at 0.3.33 rather than the 0.3.34 that PETSc 3.26.0 downloads by default,
because 0.3.34 hangs in threaded direct solves (MUMPS, SuperLU_DIST, and STRUMPACK) when
`OMP_NUM_THREADS` is greater than one.
