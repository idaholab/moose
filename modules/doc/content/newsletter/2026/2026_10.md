# MOOSE Newsletter (October 2026)

*This newsletter was drafted with AI assistance from the month's merge history.*

## MOOSE Improvements

### Block-pair interfaces in BreakMeshByBlockGenerator

[BreakMeshByBlockGenerator.md] now always creates separate directional interface boundaries
on both sides of each cut as part of the distributed mesh support work
(see [idaholab/moose#32309](https://github.com/idaholab/moose/pull/32309)). Splitting duplicates
nodes along the selected block interfaces. To track the resulting disconnected neighbor
relationships, libMesh relies on pairs of interface boundaries, such as `blockA_blockB` and
`blockB_blockA`, with separate boundary IDs.

As a result, the parameters `split_interface`, `add_interface_on_two_sides`, and
`split_transition_interface` are deprecated. Users should remove these parameters from their
BreakMeshByBlockGenerator settings. Explicitly setting any of them to `true` produces a
deprecation warning; setting one to `false` produces an error. Interfaces are always created
on both sides and split by block pair, including interfaces between `surrounding_blocks` and
the rest of the mesh.

Previously, a single generic `interface` boundary could contain several block pairs. Unless
users checked all of them, a cohesive law applied to that boundary could also act on interfaces
they did not intend to include. This combined boundary is no longer generated. Explicit
block-pair names make the selected interfaces clear in the input file.

Users should specify the appropriate interface boundary name in the corresponding interface
kernel. For example, `blockA_blockB` identifies the interface sides on `blockA` facing `blockB`:

```text
[InterfaceKernels]
  [interface]
    type = SomeInterfaceKernel
    boundary = blockA_blockB
  []
[]
```

The parameters `interface_name`, `add_transition_interface`, and `interface_transition_name`
have also been removed. Input files referring to the former combined `interface` or
`interface_transition` boundaries should use the appropriate block-pair names instead.

### Apps can now use fewer threads than the process-wide count

Thread count is now a per-app property. The maximum number of threads is set using the
`--n-threads` command line argument. An app can then set [!param](/Application/num_threads) in its
`[Application]` block to request fewer threads than were set in `--n-threads`, so a MultiApp can
give many threads to a sub-app that scales well with them, while making other apps use fewer.
([idaholab/moose#31489](https://github.com/idaholab/moose/pull/31489))

### More selective AD computations in boundary conditions and mortar

Automatic differentiation is no longer performed by `ADIntegratedBC` for element volumes in cases
when the only consumers of the derivatives were on faces to avoid unnecessary operations that were
previously performed.
([idaholab/moose#33852](https://github.com/idaholab/moose/pull/33852))
AD mortar face reinitialization on a displaced mesh likewise computed AD gradients at every mortar
quadrature point even when the constraint used none. Computed values are unchanged in both cases.
([idaholab/moose#33959](https://github.com/idaholab/moose/pull/33959))

### Automatic contact pairing supports distributed meshes and recover

`ContactPairLowerDBlockGenerator` has been renamed [AutomaticContactPairingGenerator.md] and is now
the only place contact pairs are detected, for every contact formulation. It stores them as mesh
meta-data, which [ContactAction.md] reads instead of repeating the search, so they are reloaded
after `--recover`; the search is also parallel-safe now, so `-p2 --distributed-mesh`
works where it previously failed. A plain `[Mesh] file = ...` now errors, directing the user to
[FileMeshGenerator.md].
([idaholab/moose#33979](https://github.com/idaholab/moose/pull/33979))

### MFEM backend improvements

- An [MFEMProblem.md] can now set up several `EquationSystems` instead of one, declared through the
  new [MFEMWeakForm.md] family ([MFEMComplexWeakForm.md], [MFEMEigenproblemWeakForm.md], and
  [MFEMTimeDependentWeakForm.md]) and attached with [AddMFEMWeakFormAction.md],
  [SetMFEMEquationSystemsAction.md], and [SetMFEMProblemOperatorsAction.md]. This is aimed at block
  preconditioners, whose blocks may be formed from deliberately simplified operators.
  ([idaholab/moose#33492](https://github.com/idaholab/moose/pull/33492))
- All MFEM solvers now set up their preconditioners the same way and at the same stage, which
  removes stub wrappers for solvers such as `MatrixFreeAMS` and allows preconditioners such as
  `OperatorChebyshevSmoother` that the old arrangement ruled out.
  ([idaholab/moose#34028](https://github.com/idaholab/moose/pull/34028))
- A libMesh app can now spawn several MFEM apps.
  ([idaholab/moose#33741](https://github.com/idaholab/moose/pull/33741))
- Sampler point coordinates now appear in outputs that precede any postprocessor.
  ([idaholab/moose#33741](https://github.com/idaholab/moose/pull/33741))
- New [MFEMMeridionalCurlAux.md] computes the cylindrical-coordinate curl of an azimuthal vector
  potential, giving `B_r = -dA_theta/dz` and `B_z = dA_theta/dr + A_theta/r`. The Cartesian 2D curl
  omits the `A_theta/r` term, so axisymmetric magnetostatic formulations solving for `A_theta`
  could not recover the magnetic flux density before.
  ([idaholab/moose#33655](https://github.com/idaholab/moose/pull/33655))
- [MFEMVectorProjectionAux.md] and [MFEMComplexVectorProjectionAux.md] take a new `coefficient`
  parameter that scales the projected vector.
  ([idaholab/moose#33654](https://github.com/idaholab/moose/pull/33654))
- MFEM problem operators now measure the time forming the system separately from solving it, so
  the assembly cost no longer has to be inferred from the executioner total.
  ([idaholab/moose#33844](https://github.com/idaholab/moose/pull/33844))
- An MFEM object restricted to a block or boundary name the mesh does not have now reports a MOOSE
  input error naming it, instead of aborting inside MFEM.
  ([idaholab/moose#34203](https://github.com/idaholab/moose/pull/34203))
- A bug was fixed wherein a curl-curl element matrix was sized incorrectly rather than as the number
  of DOFs squared, tripping an MFEM assertion.
  ([idaholab/moose#34151](https://github.com/idaholab/moose/pull/34151))

### Kokkos backend

- Kokkos systems now support automatic equation left-scaling by setting `automatic_scaling = true`
  in the executioner.
  ([idaholab/moose#33867](https://github.com/idaholab/moose/pull/33867))
- Kokkos system setup now sends to actual neighbors rather than scattering to every MPI rank when
  building the DOF maps for overlapping DOFs, removing half of the setup cost observed on large
  weak scaling runs on Frontier and Aurora.
  ([idaholab/moose#33937](https://github.com/idaholab/moose/pull/33937))
- CUDA is now initialized before MPI, which OpenMPI requires in order to bring up the shared-memory
  RDMA transport between GPUs; NVLink was silently falling back to PCI. On a Griffin run, processor
  communication dropped from 2.03 s to 0.015 s.
  ([idaholab/moose#33585](https://github.com/idaholab/moose/pull/33585))
- Mixing regular and Kokkos residual objects no longer crashes, because COOrdinate-format
  preallocation no longer discards matrix options such as `MAT_KEEP_NONZERO_PATTERN`.
  ([idaholab/moose#33954](https://github.com/idaholab/moose/pull/33954))
- Further Kokkos fixes cover the object-adding APIs, default coupled gradient and nodal value
  access, missing hooks in Kokkos functions, sideset ID caching, an element with the same sideset
  on several sides, derivative material APIs, and a segfault on an empty jagged array.
  ([idaholab/moose#33985](https://github.com/idaholab/moose/pull/33985))

### Mesh generation and partitioning

- [AdvancedExtruderGenerator.md] takes a new
  [!param](/Mesh/AdvancedExtruderGenerator/side_boundary), collecting the lateral surface formed by
  extruding the exterior sides of the input mesh into a named boundary. The top and bottom
  boundaries could already be named from user parameters.
  ([idaholab/moose#34095](https://github.com/idaholab/moose/pull/34095))
- [PetscExternalPartitioner.md] now handles meshes whose dual graph contains edges that are not
  face neighbors, which libMesh adds for lower-dimensional elements on a block, for spline DOF
  constraints on IsoGeometric Analysis meshes, and for the active children of a refined neighbor.
  The partitioner previously stopped with an inconsistent-neighbor-count error.
  ([idaholab/moose#34050](https://github.com/idaholab/moose/pull/34050))
- `PetscExternalPartitioner` also no longer crashes inside PTScotch when weights are used and a
  rank's partition is empty, which happened with more ranks than elements.
  ([idaholab/moose#33836](https://github.com/idaholab/moose/pull/33836))

### Input and parameter error reporting

- A missing required parameter is now reported before private or unused parameter errors, which
  previously hid the message with the simple fix of providing the required parameter.
  ([idaholab/moose#33196](https://github.com/idaholab/moose/pull/33196))
- The `index`/`component` parameters of [MaterialRealDenseMatrixAux.md],
  `MaterialStdVectorRealAux`, and their relatives are now required rather than defaulting to 0,
  which silently gave one component of an array material property.
  ([idaholab/moose#33806](https://github.com/idaholab/moose/pull/33806))
- [ArrayDiffusion.md], [ArrayReaction.md], `ArrayTimeDerivative`, `ADArrayReaction`, and
  `ArrayDGDiffusion` now check at setup that each array material property coefficient has one entry
  per array variable component, so optimized builds error instead of reading out of bounds.
  ([idaholab/moose#33891](https://github.com/idaholab/moose/pull/33891))

### Preconditioning and solver setup

A user-specified `SMP` block previously defaulted to `full = false`, so adding a
[Preconditioning](syntax/Preconditioning/index.md) block to a `NEWTON` input silently dropped the
off-diagonal Jacobian blocks the automatic preconditioner includes. `SMP` now defaults to full
coupling for `NEWTON` and `LINEAR` solves unless `full`, `off_diag_row`/`off_diag_column`, or
`coupled_groups` is specified, and the automatic preconditioner is now created per nonlinear
system.
([idaholab/moose#34036](https://github.com/idaholab/moose/pull/34036))

The kernel coverage check is now restricted, per nonlinear system, to the intersection of the
blocks the `Problem` selects and the blocks holding that system's field variables. Valid
multi-system inputs with block-restricted variables previously had to disable
`kernel_coverage_check` entirely.
([idaholab/moose#33919](https://github.com/idaholab/moose/pull/33919))

### CSV files with mixed data types

The new `MixedDataDelimitedFileReader` reads a CSV file as strings and converts only the requested
column, so a file whose columns hold differing types can be used when only some are needed; objects
reading CSV data previously required one type per column throughout.
[CSVTimeSequenceStepper.md] is the first consumer.
([idaholab/moose#34062](https://github.com/idaholab/moose/pull/34062))

### AI-assisted development

`AGENTS.md` now requires a `PetscJacobianTester` test for every hand-coded Jacobian change,
covering each coupling and coordinate system it affects, because a correct residual does not imply
a correct Jacobian. A new `issue-create` skill drafts issues following the repository's templates.
([idaholab/moose#34091](https://github.com/idaholab/moose/pull/34091))

A new script reports why CIVET CI failed on a pull request: which jobs really failed, the build
errors or failing tests inside them, a clustering of error signatures, and a reproduce command. It
needs no CIVET credentials, and the accompanying `civet-ci-failures` skill documents how to read
the report.
([idaholab/moose#33756](https://github.com/idaholab/moose/pull/33756))

An `update-packages` skill covering the monthly distributed-package update was added alongside this
month's package bump.
([idaholab/moose#33833](https://github.com/idaholab/moose/pull/33833),
[idaholab/moose#33879](https://github.com/idaholab/moose/pull/33879))

### TestHarness

- On Linux, test memory is now measured as `Pss - Pss_File`, where Pss_file is the proportional
  set size (Pss) of memory pages that are backed by files. The previous measurement that was
  based directly on `Pss` charged a test running alone for nearly all the executable and library pages
  shared by every running test, so small tests were intermittently killed with "OVER MEMORY" on CIVET.
  `RESULTS_VERSION` was increased to 10, and 55 now-unnecessary `min_slots` entries were removed.
  ([idaholab/moose#34075](https://github.com/idaholab/moose/pull/34075))
- Output that cannot be decoded as UTF-8 no longer fails a test or drops the stream it came from.
  ([idaholab/moose#34112](https://github.com/idaholab/moose/pull/34112))
- `SchemaDiff` previously compared string lists containing negative values incorrectly, carrying the
  same sign errors fixed for scalars in #33304: `"1 -2"` compared equal to `"1 -2.5"`, and `"1e-11 1"`
  to `"2e-11 2"`. This bug has been fixed.
  ([idaholab/moose#33980](https://github.com/idaholab/moose/pull/33980))

### Documentation and MooseDocs

- The MooseDocs search index and generated anchors no longer split a name such as `HeatPipe3Phase`
  into "HeatPipe 3 Phase". Heading anchors and page titles change accordingly, for example
  "quad-4-faces" becomes "quad4-faces".
  ([idaholab/moose#34074](https://github.com/idaholab/moose/pull/34074))
- The MooseDocs listing extension now tries a strict block-name match before a loose one. A block
  whose name ends with another's shadowed it, so a page requesting `Kernels` previously was given
  `AuxKernels` whenever the latter came first in the input file, but it would now be given `Kernels`.
  ([idaholab/moose#33996](https://github.com/idaholab/moose/pull/33996))

### Miscellaneous

- `CSGBase::getLinkedCSGObjects` now skips a universe it has already visited. A lattice can place
  the same universe at many positions, and repeating the traversal for each one was slow on
  realistic pin-assembly-core geometries.
  ([idaholab/moose#34057](https://github.com/idaholab/moose/pull/34057))
- A dedicated MOOSE header symlink directory is now created when an application and MOOSE are
  built side by side, which previously failed the build on macOS and WSL from a fresh clone of
  each.
  ([idaholab/moose#33804](https://github.com/idaholab/moose/pull/33804))
- Several test-only objects moved out of the framework into test applications, reducing what a
  production build compiles: `MaterialDerivativeTestAction` and its kernels, the
  `[Debug/MaterialDerivativeTest]` block, `ConvectiveFluxBC`, `TestNewmarkTI`, and
  `TestSourceStepper`. Applications using any of them from the framework have been patched to
  either provide their own or use alternative objects.
  ([idaholab/moose#33926](https://github.com/idaholab/moose/pull/33926))
- Interface kernels now contribute on a sideset whose coarse side faces refined elements. The
  coarse element's neighbor is an inactive ancestor once it is cut into finer elements, so the
  whole face was previously skipped; the coarse side is now assembled against each active child in
  turn.
  ([idaholab/moose#33963](https://github.com/idaholab/moose/pull/33963))
- IsoGeometric Analysis initial conditions are now projected rather than interpolated where spline
  nodes should not be evaluated directly, since interpolated initial conditions are less accurate
  on body-fit meshes and potentially unusable on flex meshes.
  ([idaholab/moose#34055](https://github.com/idaholab/moose/pull/34055))
- `PetscJacobianTester` now judges a Jacobian by the relative measure
  `||J - Jfd||_F / ||J||_F < ratio_tol` alone, because `difference_tol` now defaults to infinity.
  The absolute difference scales with the magnitude of the Jacobian entries, so the old default of
  `1` incorrectly failed for correct Jacobians on finite-difference noise whenever the entries were
  large.

## MOOSE Bug Fixes

### Jacobian correctness

- `ADScalarKernel` passed every component of a scalar variable's residual in one `addJacobian`
  call, but such a call requires all of its rows to depend on the same degrees of freedom, which
  higher-order scalar components need not. Optimized builds dropped the later components, so a
  `SECOND` order variable lost its second row and the Jacobian was singular. Components are now
  added separately.
  ([idaholab/moose#33967](https://github.com/idaholab/moose/pull/33967))
- An active `NodalKernel` was previously collected once per block of the node it was active on, so
  its Jacobian was added several times on nodes shared by subdomains while the residual loop executed
  it once. Newton's method therefore lost quadratic convergence. This has been corrected, and results
  are unchanged elsewhere.
  ([idaholab/moose#33972](https://github.com/idaholab/moose/pull/33972))
- AD residual and Jacobian caching skipped libMesh constraint application whenever a single
  residual was added, assuming such calls come from finite volume objects. On a DOF constrained by
  a periodic boundary condition or a hanging node, the contribution was silently lost rather than
  distributed to the constraining DOFs. The shortcut is now taken only for unconstrained DOFs,
  excluding `ADNodalBC` Jacobian rows, which would otherwise leave the Jacobian singular.
  ([idaholab/moose#33969](https://github.com/idaholab/moose/pull/33969))
- Variables of other solver systems were previously indexed differently from auxiliary variables, so
  kernels relying on the jvar map, such as those in solid mechanics and phase field, formed an
  inexact Jacobian under multi-system solves. This has been corrected.
  ([idaholab/moose#33977](https://github.com/idaholab/moose/pull/33977))
- An array variable's second time derivative was read from the first-derivative vector, so
  `coupledArrayDotDot()` returned the first time derivative. This affects array variables under a
  second-order time integrator such as `NewmarkBeta`.
  ([idaholab/moose#34107](https://github.com/idaholab/moose/pull/34107))

### Exception handling and timestep rejection

- A user object throwing an exception on only some MPI ranks hung the simulation: the ranks that
  threw went straight to the exception handler, which communicates, while the others waited in a
  `finalize()` communication. This affected element, side, nodal, mortar, and general user objects
  alike. Each stage now records its exceptions without communicating, and every rank reaches one
  check before that stage's `finalize()`.
  ([idaholab/moose#33909](https://github.com/idaholab/moose/pull/33909))
- A non-finite displaced mesh coordinate, which could occur after a failed linear solve, now throws a
  `MooseException` so the time step is cut, rather than the run aborting later inside mortar
  generation.
  ([idaholab/moose#34035](https://github.com/idaholab/moose/pull/34035))
- A [Terminator.md] user object in a soft-fail mode left the fixed point status unset, so a
  transient with fixed point iterations hit `Internal error: wrong fixed point status!` instead of
  failing the step and reducing the time step size. This has been corrected.
  ([idaholab/moose#33962](https://github.com/idaholab/moose/pull/33962))
- `XFEM` now discards crack-growth marks left by a rejected timestep attempt, since valid marks
  always come from the previous timestep.
  ([idaholab/moose#34004](https://github.com/idaholab/moose/pull/34004))
- `--test-restep` fails one timestep on purpose to check that a rejected step leaves no stale
  state, but with `Executioner/abort_on_solve_fail = true` that forced failure ended the run. It no
  longer aborts; any other failed solve still does.
  ([idaholab/moose#33999](https://github.com/idaholab/moose/pull/33999))

### Contact and mortar fixes

- Penalty mortar contact previously lost its history across `--recover`. [PenaltyFrictionUserObject.md]
  and [PenaltyWeightedGapUserObject.md] kept friction history and augmented Lagrange (AL) multipliers
  in maps keyed by pointer, which cannot be checkpointed, so a recovered run silently continued
  from zero history, affecting computed contact forces. The maps are now keyed by node ID and
  restartable.
  ([idaholab/moose#34128](https://github.com/idaholab/moose/pull/34128))
- The same two user objects now save their AL state at the start of each timestep and restore it
  when the step is retried.
  ([idaholab/moose#34001](https://github.com/idaholab/moose/pull/34001))
- The AL update of a slipping node set its total tangential traction to
  `penalty_friction * |normal_lm|` instead of the Coulomb cone value `mu * |normal_lm|`, so the
  multiplier could be off by orders of magnitude and the AL loop did not converge to the Coulomb
  solution there. This has been corrected, and frictional AL results change as a result.
  ([idaholab/moose#34100](https://github.com/idaholab/moose/pull/34100))
- `AugmentedLagrangianContactConvergence` now passes its incremented iteration count back to the
  problem, so `maximum_lagrangian_update_iterations`, node-face `penalty_multiplier` growth, and
  `NumAugmentedLagrangeIterations` all see the correct count.
  ([idaholab/moose#34038](https://github.com/idaholab/moose/pull/34038))
- The quasi-static mortar friction constraint passed a sliding speed of zero to
  `function_friction`, so speed-dependent friction had no effect. The sliding speed is now the
  mortar-projected nodal slip rate of Wohlmuth (2011, Acta Numerica, eq. 3.10a). Constant and
  pressure-only friction are unchanged.
  ([idaholab/moose#34016](https://github.com/idaholab/moose/pull/34016))
- Dynamic mortar contact passed a sliding speed several times too large to a speed-dependent
  friction law, which could drive the friction coefficient negative; it now uses the same quantity
  as the quasi-static constraint, and a constant `mu` must be positive.
  ([idaholab/moose#34020](https://github.com/idaholab/moose/pull/34020))
- The 3D mortar nearest-neighbor search examined only node IDs below the mesh's node count, but
  `allow_renumbering = false` leaves gaps in the IDs. Mortar segments depending on primary nodes
  above the count were dropped with only a warning, which could switch contact off across a whole
  interface, so the blocks passed through each other while the solve still converged. This has been
  corrected.
  ([idaholab/moose#34031](https://github.com/idaholab/moose/pull/34031))
- Only the owner of an inactive secondary node zeroes its Lagrange multiplier DOFs, but the
  inactive set was shared only with ranks holding a secondary element touching the node. An owner
  holding no such nodes left the node's LM rows empty, so LU solvers hit a zero pivot and the run
  aborted. This has been corrected.
  ([idaholab/moose#34033](https://github.com/idaholab/moose/pull/34033))
- Mortar segment mesh statistics segfaulted where no mortar segments form, which is exactly the
  case `debug_mesh = true` and `MortarSegmentMeshReporter` exist to diagnose. This has been
  corrected, and zero values are reported in that case.
  ([idaholab/moose#34174](https://github.com/idaholab/moose/pull/34174))
- [MortarUserObjectAux.md] checked the wrong user object type before reading `active_set` and
  `delta_tangential_lm_one`/`two`, so the active set could not be output for frictionless penalty
  contact, and requesting these quantities from a Lagrange multiplier friction user object
  segfaulted instead of giving an input error. These quantities are now correctly output.
  ([idaholab/moose#34139](https://github.com/idaholab/moose/pull/34139))
- [MortarGenericTraction.md] previously segfaulted at the first residual evaluation when
  `use_displaced_mesh = true` was omitted, because the cohesive zone user object it reads traction
  from always runs on the displaced mesh. The parameter now defaults to `true` and `false` is an
  input error; every existing block already sets it, so that line can now be omitted.
  ([idaholab/moose#34144](https://github.com/idaholab/moose/pull/34144))
- Custom dual coefficients are no longer recomputed for lower-dimensional FE types that never
  requested dual shape data. On second-order meshes a mixed-order mortar discretization with a
  first-order dual Lagrange multiplier could try to factor an unused second-order Gram matrix, and
  libMesh threw if it was singular.
  ([idaholab/moose#33907](https://github.com/idaholab/moose/pull/33907))
- `CohesiveZoneModelBase` built the primary-side displacement gradients from the local rather than
  the neighbor gradient, so the interface deformation gradient used only the secondary side.
  Now the gradients from both sides are used, which changes results for mortar cohesive zone models
  wherever the deformation differs across the interface.
  ([idaholab/moose#34009](https://github.com/idaholab/moose/pull/34009))
- `lag_displacement_jump` on [BilinearMixedModeCohesiveZoneModel.md] is now deprecated. It was declared
  but never read, so `true` and `false` always gave identical results.
  ([idaholab/moose#34134](https://github.com/idaholab/moose/pull/34134))

### Miscellaneous

- [MOOSEQuantityToNEML2.md] read `VARIABLE` inputs without declaring a variable dependency, so when
  another user object in the same loop declared one, the NEML2 input variable was left stale or
  zero. This was fixed by declaring the variable dependencies as expected.
  ([idaholab/moose#34187](https://github.com/idaholab/moose/pull/34187))
- MOOSE registered its own SNES function and Jacobian callbacks on the top-level `DMMoose`, but
  libMesh registers its own on the same DM afterwards through the same entry points, so the MOOSE
  callbacks were replaced before PETSc could call them. They are now removed.
  ([idaholab/moose#34093](https://github.com/idaholab/moose/pull/34093))
- Apps without a Console output (e.g. `[Outputs] console = false`) no longer keep every message
  written to `_console` in memory. The buffer was never cleared and was copied at every flush, so
  long-running (sub-)apps, such as a MultiApp running many solves in one process, grew slower as
  the number of messages increased.
  ([idaholab/moose#34118](https://github.com/idaholab/moose/issues/34118))

## MOOSE Modules Changes

### Contact module

Mechanical mortar contact now assembles the contact force by interpolating the nodal traction
vector with the traction basis, instead of scaling an interpolated scalar pressure by the nodal
normal of the residual row's own node. Only the former is the transpose of the weighted gap, so the
contact force is now self-equilibrated across the interface and no longer depends on secondary node
numbering. Contact forces and converged results therefore change on interfaces where the secondary
nodal normals vary along the face.

Local-basis quasistatic `mortar` and `mortar_penalty` contact Jacobians now also include
derivatives of the averaged secondary nodal normals and their tangent basis. These derivatives can
require a larger AD container on high-order or high-valence interfaces. Because the contact
coupling changes during the solve in most contact problems, such as when surfaces slide or come into
contact, set `Problem/use_hash_table_matrix_assembly = true` to accommodate the changing sparsity
pattern.
([idaholab/moose#33390](https://github.com/idaholab/moose/pull/33390))

### Solid Mechanics module

- New [SecondDerivativeRegularization.md] and `ADSecondDerivativeRegularization` kernels add a
  regularization term built from second derivatives of a scalar variable, selected with
  `regularization = huhu`, `lulu`, or `huhu_lulu` and scaled by a required `coefficient`. The
  terminology comes from HuHu/LuLu regularization in third-medium contact, but the kernels are
  general; for a vector field, add one per component.
  ([idaholab/moose#32974](https://github.com/idaholab/moose/pull/32974))
- The `BiLinearMixedModeTraction` cohesive zone material model recovered the wrong Mode II
  fracture energy and had an inconsistent hand-coded Jacobian. The pure Mode II final separation
  carried an extra factor of `sqrt(2)`, `delta_f = 2*sqrt(2)*GIIc/S` rather than the
  `delta_f = 2*GIIc/S` that energy consistency requires. Both issues are fixed.
  ([idaholab/moose#33902](https://github.com/idaholab/moose/pull/33902))

### Porous Flow module

- New [TabulatedPVTFluidProperties.md] reads PVDO/PVDG-style black-oil PVT data: a density at
  standard conditions, and an isothermal table of pressure, formation volume factor B, and
  viscosity. Following black-oil convention, `1/B` and `1/(B*mu)` are interpolated linearly in
  pressure, giving exact pressure derivatives.
  ([idaholab/moose#34113](https://github.com/idaholab/moose/pull/34113))
- New [PorousFlowPorosityVinsomeWesterveld.md] captures the thermal opening of a lower-dimensional
  fracture as cold injection cools and contracts the adjacent rock. It subtracts
  `thermal_opening_coeff * I` from [PorousFlowPorosityLinear.md], where `I` is the heat content of
  the adjacent matrix by the semi-analytic method of Vinsome and Westerveld (1980), needed because
  the cooled layer is thinner than a matrix element.
  ([idaholab/moose#34049](https://github.com/idaholab/moose/pull/34049))
- `porosity_min` was moved into `PorousFlowPorosityBase`, so every porosity Material can now enforce
  a lower bound rather than only [PorousFlowPorosityLinear.md] and `PorousFlowPorosityExponentialBase`.
  ([idaholab/moose#33950](https://github.com/idaholab/moose/pull/33950))
- [PorousFlowBrineCO2.md], [PorousFlowWaterNCG.md], and the other `PorousFlowFluidState` user
  objects take new `compute_enthalpy` and `compute_internal_energy` flags. Profiling found a case
  spending 26% of its time computing enthalpy and internal energy for an isothermal model that
  never used either. This computation can now be avoided by using those new flags.
  ([idaholab/moose#33349](https://github.com/idaholab/moose/pull/33349))
- The volumetric strain kernels and materials are now templated for AD:
  [PorousFlowMassVolumetricExpansion.md], [PorousFlowHeatVolumetricExpansion.md],
  [PorousFlowDesorpedMassVolumetricExpansion.md], [PorousFlowFullySaturatedMassTimeDerivative.md],
  [PorousFlowPorosity.md], and [PorousFlowVolumetricStrain.md]. This continues the work of letting
  the FE kernels use the AD materials the FV kernels already use.
  ([idaholab/moose#33754](https://github.com/idaholab/moose/pull/33754))
- `PorousFlowDarcyBase` weighted the Darcy flux by the non-AD `_JxW * _coord` in both flavors. On
  a displaced mesh with the displacements as variables, the AD weight carries `d(JxW)/d(disp)`, so
  the displacement Jacobian block was missing that term for the four AD advective flux and heat
  advection kernels. That term was added to the Jacobian. The residual was already correct and was
  not modified.
  ([idaholab/moose#33995](https://github.com/idaholab/moose/pull/33995))

### Navier-Stokes module

- Conjugate heat transfer interfaces solved with the LinearFV segregated (SIMPLE) solver can now
  include surface-to-surface radiation. Setting
  [!param](/Executioner/SIMPLE/surface_radiation_object_name) to a
  [GrayLambertSurfaceRadiationBase.md] user object, such as
  [ViewFactorObjectSurfaceRadiation.md], adds the net outward radiative heat flux to the energy
  balance on every CHT interface belonging to it.
  ([idaholab/moose#33743](https://github.com/idaholab/moose/pull/33743))
- CHT interfaces now also take [!param](/Executioner/SIMPLE/thermal_resistance), an area-normalized
  thermal resistance in m^2*K/W given as one functor for all interfaces or one per interface.
  ([idaholab/moose#33772](https://github.com/idaholab/moose/pull/33772))

### Thermal Hydraulics module

- THM Components can now participate in multi-system solves, through an optional solver system name
  which defaults to `nl0`, so existing inputs are unaffected.
  ([idaholab/moose#33925](https://github.com/idaholab/moose/pull/33925))
- New scalar kernels add a path-integrated incompressible flow capability:
  [IncompressibleMomentumSPScalarKernel.md] and
  [CoupledPressureIncompressibleMomentumSPScalarKernel.md] integrate 1D momentum along a flow path
  of geometrically varying segments acting on a mass flow rate scalar variable, and
  [IncompressibleEnergySPScalarKernel.md] does the same for energy. This is intended among other
  things as a basis for species transport studies.
  ([idaholab/moose#33692](https://github.com/idaholab/moose/pull/33692))
- Those same kernels fetched coupled scalar variables through the non-AD accessor rather than the
  templated one, silently zeroing the off-diagonal Jacobian entries of their AD instantiations.
  ([idaholab/moose#34064](https://github.com/idaholab/moose/pull/34064))

### Subchannel module

- The Pacio-Chen-Todreas Detailed model for hexagonal wire-wrapped assemblies is available as the
  SCM closure pair [SCMFrictionChenTodreas.md] and [SCMMixingChenTodreas.md], renamed from the
  Upgraded Cheng-Todreas classes they build on, whose pressure drop correlation it follows with
  different coefficient values. Additional friction factor verification was added to the
  documentation, including comparisons to DASSH, to the reference journal and to independent
  python implementations.
  ([idaholab/moose#33634](https://github.com/idaholab/moose/pull/33634))
- The `n_blocks` axial block-marching parameter of `SubChannel1PhaseProblem` now defaults to 1
  instead of being required, since most inputs use a single block.
  ([idaholab/moose#34046](https://github.com/idaholab/moose/pull/34046))
- An `axial_heat_rate` depending on x or y gave pin powers inconsistent with the radial power
  distribution in [SCMQuadPowerIC.md], [SCMTriPowerIC.md], [SCMQuadPowerAux.md], and
  [SCMTriPowerAux.md], because the per-pin correction evaluated the function at x = y = 0; it is
  now evaluated at each pin's nodes. Results for z-only shapes are unchanged, and a time-dependent
  `power` postprocessor is no longer applied one time step late.
  ([idaholab/moose#34083](https://github.com/idaholab/moose/pull/34083))
- The SubChannel thermo-mechanical coupling was modified to conserve the pin power exactly
  where it previously lost 1.4% of it on the way back to SCM, and is now tested in the combined
  module. An optional transfer interpolates the pin surface temperature linearly instead of
  imposing a piecewise-constant profile.
  ([idaholab/moose#34155](https://github.com/idaholab/moose/pull/34155))

### Stochastic Tools module

Parallel sampler gathering and bounded actions have been added to the deep reinforcement learning
capability, aimed at autonomous control. [LibtorchDRLControl.md] and [LibtorchDRLControlTrainer.md]
can bound the control action so the controller cannot reach a nonphysical state, and a new
[SamplerDRLControlTransfer.md] gathers observations across samplers in parallel.
([idaholab/moose#32802](https://github.com/idaholab/moose/pull/32802))

### Fluid Properties module

The new `NASA7IdealGasFluidProperties` describes H2, O2, H2O, CH4, CO, CO2, and N2 as ideal gases
whose heat capacity, enthalpy, and entropy depend on temperature through the NASA 7-coefficient
polynomials of GRI-Mech 3.0. Its enthalpies include the enthalpy of formation, so the energy of a
mixture accounts for the heat of reaction. `IdealGasMixtureFluidProperties` accepts these gases as
components. Viscosity and thermal conductivity are not yet available for them, so they cannot yet
be used in the gas-mixture flow channels of the thermal hydraulics module
([idaholab/moose#34123](https://github.com/idaholab/moose/pull/34123)).

- A NaN reaching LAPACK through a Newton solve previously crashed [TabulatedBicubicFluidProperties.md],
  seen on an Apple M4, where a fluid property evaluated out of range can return NaN in an optimized
  build without the debug-mode check catching it. The Newton inversion now checks for non-finite
  values.
  ([idaholab/moose#33921](https://github.com/idaholab/moose/pull/33921))
- [LeadLithiumFluidProperties.md] documentation was clarified. Several readers had misread the
  temperature units: the implemented formula takes Kelvin, while the original source equation was
  written in Celsius.
  ([idaholab/moose#34061](https://github.com/idaholab/moose/pull/34061))
