# MOOSE Newsletter (November 2026)

*This newsletter was drafted with AI assistance from the month's merge history.*

## MOOSE Improvements

### NEML2 v3 Integration

The MOOSE–NEML2 integration has been updated to support NEML2 v3, described in the
recent SoftwareX paper
[*Version 3—NEML2: An efficient and modular multiphysics constitutive modeling library
for hybrid computing environments*](https://doi.org/10.1016/j.softx.2026.102937).

NEML2 v3 enables Python-based constitutive model development, while the updated MOOSE
interface supports two C++ execution modes: `cpp-aoti` for ahead-of-time compiled,
Python-free model evaluation and `cpp-eager` for direct, compile-free evaluation through
an embedded Python interpreter. The integration also introduces MPI-aware CPU and GPU
device scheduling for compiled models, improves model data and derivative handling and
failure diagnostics, and simplifies NEML2 and PyTorch dependency configuration through
the active Python environment. ([idaholab/moose#34170](https://github.com/idaholab/moose/pull/34170))

### Displaced meshes now follow SECOND order displacements on face-node elements

TET14, TRI7, PYRAMID18, PRISM20, and PRISM21 elements carry nodes on which a `SECOND` order
Lagrange variable has no degrees of freedom, and the displaced mesh update moved only nodes that
have them, so volumes, quadrature points, normals, and contact surfaces were computed on distorted
elements and large displacements inverted them. The displacement at such nodes is now interpolated
from the face they lie on, independently of the partitioning, with AD Jacobians still exact.
`SECOND` order meshes therefore no longer require `SECOND` order displacements, except on PRISM21.
([idaholab/moose#34040](https://github.com/idaholab/moose/pull/34040))

### AD geometry maps on displaced meshes are built only when used

On a displaced mesh, any AD object made every element compute the AD element map and AD shape
function gradients even when nothing read them. The map gives each element node its displacement
derivatives, so a HEX27 element exceeded the default AD derivative size of 64 and forced a larger
`--with-derivative-size`. Both are now built only on request, and a 3D HEX27 sliding mortar contact
case runs at derivative size 64 instead of 512.
([idaholab/moose#34349](https://github.com/idaholab/moose/pull/34349))
The same treatment on faces drops that case's wall time from 572 s to 518 s with an identical
residual history, and `ADInterfaceKernel` and `AnisoHeatConductionMaterial` now read the AD face
quadrature points rather than the volume ones, which corrects the boundary values of the latter.
([idaholab/moose#34335](https://github.com/idaholab/moose/pull/34335))

### Patterned reactor meshes stitch pairwise instead of onto one growing mesh

[PatternedHexMeshGenerator.md] and [PatternedCartesianMeshGenerator.md] stitched each pattern site
onto a single mesh that grew with every call, so the cost was quadratic in the number of sites. With
`pattern_boundary = none`, neighboring sites are now stitched in pairs, for O(N log N) cost: a
47-ring hex lattice of 6769 sites drops from about 46 minutes to about 24 seconds in serial. Element
and node numbering are unchanged, but each cell is translated once rather than forward and back, so
cell coordinates differ at the 1e-13 level, which can change a downstream `XYDelaunayGenerator`
triangulation.
([idaholab/moose#34430](https://github.com/idaholab/moose/pull/34430))

### Node-to-block relation stored per node instead of as a set per node

`MooseMesh` now stores one subdomain ID per node, keeping a full set only for nodes on a subdomain
interface; `getNodeBlockIds()` keeps its signature, so callers are unaffected. On a single-block
262144-element cantilever on 24 ranks, `cacheInfo()` drops from 0.517 s to 0.041 s and no longer
holds about 140 MB per rank. On a serial mesh of the same size split into 8 blocks it drops from
0.36 s to 0.11 s.
([idaholab/moose#33850](https://github.com/idaholab/moose/pull/33850))

### Physics objects can share a variable across the union of their blocks

Several [Physics](syntax/Physics/index.md) objects can now request the same variable and have it
created once on the union of their blocks, instead of the input declaring a shared variable and each
Physics suppressing its own. [PhysicsVariableCoordinator.md] collects the requests and checks that
the parameters other than `block` agree. For finite volume variables it rejects sharing across
touching subdomains, where both Physics would restrict their flux kernels away from the shared face
and leave an implicit zero-flux wall.
([idaholab/moose#34259](https://github.com/idaholab/moose/pull/34259))

### Controls can repeat a failed time step without the predictor

A time step whose predicted solve fails could only be retried with a smaller `dt`, and not at all at
`dtmin`, although retrying once without the predictor often converges. A
[Controls](syntax/Controls/index.md) object can now set that up from the input alone: controls run
on the new `FAILED` flag, predictors have a controllable `apply` parameter,
`cutback_factor_at_failure` is controllable and may be 1 to repeat the step at the same size once
per time step, and [NumFailedTimeSteps.md] takes a `current_time_step_only` option.
([idaholab/moose#34338](https://github.com/idaholab/moose/pull/34338))

### Per-variable absolute tolerances in reference residual convergence

[ReferenceResidualConvergence.md] and `ReferenceResidualProblem` take `variable_nl_abs_tol`, a map
giving selected variables their own absolute tolerance while unlisted variables keep `nl_abs_tol`.
Variables in one group must share a tolerance, since a group has a single residual norm. This
converges problems whose variable residuals differ by many orders of magnitude, where no single
`nl_abs_tol` works.
([idaholab/moose#34305](https://github.com/idaholab/moose/pull/34305))

### Constant nullspace modes for singular Jacobians

The `[Problem]` block takes `constant_null_space_variables` and
`constant_transpose_null_space_variables`. Each listed variable contributes one mode that is one on
its degrees of freedom and zero elsewhere, attached to the Jacobian as its nullspace or transpose
nullspace and rebuilt on each request. A transpose nullspace pressure mode projects the round-off
component of a mass residual sum out of the right hand side, which GMRES otherwise stagnates on.
([idaholab/moose#34351](https://github.com/idaholab/moose/pull/34351))

### Execution order groups for auxiliary kernels

Auxiliary kernels moved into `TheWarehouse`, which already implements execution order groups, so
array and regular auxiliary kernels can now be ordered relative to each other through
[AuxKernels](syntax/AuxKernels/index.md).
([idaholab/moose#32357](https://github.com/idaholab/moose/pull/32357))

### AD second derivatives and divergences of coupled variables

`adSecondSln()` is now filled for array variables and `adCoupledArraySecond()` exposes the second
derivatives of a coupled array variable, so an AD kernel can form a biharmonic term on an array
variable with an exact Jacobian.
([idaholab/moose#34291](https://github.com/idaholab/moose/pull/34291))
`adDivSln()` and `adCoupledDiv()` do the same for the divergence of vector finite element variables,
mirroring the existing AD curl.
([idaholab/moose#34289](https://github.com/idaholab/moose/pull/34289))

### Functors can be evaluated at a bare physical point

`FunctorBase` gained a `PointArg` overload, so a functor can be evaluated, differentiated, and
time-differentiated at a physical point with no mesh information; functors needing mesh information,
such as field variables, report an error. `ADScalarKernel` now inherits from `ADFunctorInterface`,
which lets a scalar kernel read functors. Applications with their own functors need updating.
([idaholab/moose#34192](https://github.com/idaholab/moose/pull/34192))

### `save_in` and `diag_save_in` are deprecated in the framework

`save_in` and `diag_save_in` on kernels, boundary conditions, DG kernels, interface kernels, and
nodal kernels are deprecated in favor of the more capable tagging system: add the residual to a
tagged vector with `extra_vector_tags` and read it with a `TagVectorAux`, or add the Jacobian to a
tagged matrix with `extra_matrix_tags` and read its diagonal with a `TagMatrixAux`.
([idaholab/moose#34498](https://github.com/idaholab/moose/pull/34498))

### DomainUserObject can select its external boundaries

`DomainUserObject` ran its boundary callback on every boundary not used as an interface. It now
takes an optional `boundaries` parameter: unset keeps that behavior, an empty list disables boundary
evaluation, and a list selects the boundary IDs to evaluate, leaving element, internal-side, and
interface evaluation alone. The [UserObjects](syntax/UserObjects/index.md) page documents how a
side's neighbor and boundary IDs are dispatched to those four operations.
([idaholab/moose#34422](https://github.com/idaholab/moose/pull/34422))

### New framework objects

- [CoefVectorTimeDerivative.md] multiplies the vector time derivative by a constant coefficient, the
  `LAGRANGE_VEC` counterpart of `CoefTimeDerivative`, needed for equations such as the
  magnetoquasistatic vector potential.
  ([idaholab/moose#34185](https://github.com/idaholab/moose/pull/34185))
- [CumulativeTimeAverageFunctorAux.md] computes the running time-weighted mean of a functor from
  `start_time`, for example the mean field of an unsteady simulation.
  [TimeWindowedStatisticsPostProcessor.md] reports the `mean`, `std`, or another `statistic` of a
  postprocessor over the last `window` time steps, which monitors whether a quantity in a
  statistically steady simulation has settled.
  ([idaholab/moose#34279](https://github.com/idaholab/moose/pull/34279))
- The `[ConstructiveSolidGeometry]` block is the input file equivalent of `--csg-only`, naming the
  [!ac](JSON) output file and selecting whether engineering units are expanded; see [CSGAction.md].
  `expand_units` now defaults to `true` for both the block and the command line.
  ([idaholab/moose#34352](https://github.com/idaholab/moose/pull/34352))
- `CSGBase` gained a cell and universe ownership check and a public geometry check that no longer
  requires writing the model to [!ac](JSON) first.
  ([idaholab/moose#34363](https://github.com/idaholab/moose/pull/34363))

### Input and solver setup checks

- An interface kernel silently skipped faces where `variable` is not defined on the primary side or
  `neighbor_var` on the secondary side. This is now reported at setup, with a note when the two
  variables appear to be flipped relative to the sideset orientation.
  ([idaholab/moose#34215](https://github.com/idaholab/moose/pull/34215))
- A flag in `petsc_options` now removes an earlier PETSc name-value pair of the same name, so a
  `[Preconditioning]` block's `-ksp_converged_reason` can replace the executioner's default
  `-ksp_converged_reason ::failed`.
  ([idaholab/moose#34458](https://github.com/idaholab/moose/pull/34458))
- The new global command line option `--suppress-info` omits the messages emitted through
  `mooseInfo()` and `mooseInfoRepeated()`, which are noisy when running variations of the same
  input. Warnings, deprecations, and errors are unaffected.
  ([idaholab/moose#33380](https://github.com/idaholab/moose/pull/33380))

### Exodus output names are no longer truncated at 32 characters

[Exodus.md] defaults `max_output_name_length` to 80 rather than 32, now that the applications in CI
use the longer names. Variable and block names between 33 and 80 characters appear in full, so
outputs that relied on the truncated names change.
([idaholab/moose#34156](https://github.com/idaholab/moose/pull/34156))

### MFEM backend improvements

- An [MFEML2ZienkiewiczZhuIndicator.md] without `flux_fespace` and `smooth_flux_fespace` built
  default flux spaces with as many components as the mesh has space dimensions. That is right for a
  diffusion kernel's gradient but not for elasticity, whose Voigt-notation stress has
  `dim(dim+1)/2` components, or for 3D curl-curl. The defaults now follow the kernel's flux.
  ([idaholab/moose#34201](https://github.com/idaholab/moose/pull/34201))
- `MFEMEigenproblem` added an `mfem::MassIntegrator` for every scalar-shape-function space,
  including vector H1 spaces, whose mass matrix needs one block per component; it now uses
  `mfem::VectorMassIntegrator` there.
  ([idaholab/moose#34205](https://github.com/idaholab/moose/pull/34205))
  Its boundary-condition diagonal entries for eigenproblem mass matrices are also less extreme,
  which removes a dependence on the OpenBLAS kernel the machine selects.
  ([idaholab/moose#34355](https://github.com/idaholab/moose/pull/34355))
- MFEM samplers take several variables at once through a `variables` parameter, which replaces
  `variable`, so one object can sample multiple variables at the same points.
  ([idaholab/moose#34085](https://github.com/idaholab/moose/pull/34085))

### Kokkos backend

- Kokkos kernels, boundary conditions, and nodal kernels take `variables` in place of `variable`, so
  one object can act on several standard variables and parallelize over them. This suits
  applications such as neutronics, where the same kernel applies to a flux variable per energy group
  and array variables make the per-group access cumbersome.
  ([idaholab/moose#34292](https://github.com/idaholab/moose/pull/34292))
- Kokkos objects can couple array variables and read their components through the usual `Coupleable`
  interface, although Kokkos array kernels do not exist yet.
  ([idaholab/moose#33501](https://github.com/idaholab/moose/pull/33501))
- libMesh constraints are now applied in Kokkos systems, after the kernels and boundary conditions
  and before final assembly, which is the prerequisite for periodic boundary conditions and
  hp-adaptivity.
  ([idaholab/moose#33678](https://github.com/idaholab/moose/pull/33678))
- Kokkos elemental auxiliary kernels no longer build a 30x30 mass matrix in per-thread local memory
  and factor it on the fly. The Cholesky factors are precomputed into a global array, which lifts
  the 30 degree-of-freedom-per-element limit and cuts CUDA stack memory use.
  ([idaholab/moose#34371](https://github.com/idaholab/moose/pull/34371))
- A Kokkos material property can now be checked for validity on the host as well as the device. The
  check read whether the internal data array was allocated, which is only true of the shallow copy
  made during parallel dispatch, so it always returned false on the host.
  ([idaholab/moose#34467](https://github.com/idaholab/moose/pull/34467))
- A Newton eigenvalue solve with Kokkos vectors and a HYPRE matrix aborted with
  `Incompatible offload mask PETSC_OFFLOAD_KOKKOS`. SLEPc builds its work vectors from the
  operators, whose vector type follows the matrix type, so the operators now take the system
  solution's vector type, which honors `-vec_type`.
  ([idaholab/moose#34330](https://github.com/idaholab/moose/pull/34330))

### TestHarness

The TestHarness now tracks the NVIDIA GPU memory of each test alongside its CPU memory, and
`--max-gpu-memory-per-slot` (or `MOOSE_MAX_GPU_MEMORY_PER_SLOT`) kills a test that exceeds it, so
tests sharing a GPU cannot run it out of memory. The figure comes from NVML through `pynvml`
whenever NVML finds a GPU, regardless of `--compute-device`, because every process of a CUDA build
holds a CUDA context. In the same area, `-j`, `-p`, `--n-threads`, and the memory and CPU limits
reject non-positive values, and `compute_devices` is honored by every tester rather than only
`RunApp`.
([idaholab/moose#34368](https://github.com/idaholab/moose/pull/34368))

A NULL character in test output is now a caveat rather than a failure, as invalid UTF-8 already was;
the OpenMPI 5.0.10 `cuMemHostRegister` warning ends with one. Invalid UTF-8, NULL characters, and
the JSON check share the caveat label `invalid output characters in <stream>`.
([idaholab/moose#34117](https://github.com/idaholab/moose/pull/34117))

The bundled `exodiff` segfaulted on polygonal and polyhedral meshes, so they could not be compared
against a gold file without first converting them to simplices. Connectivity is now walked element
by element, since the elements of a polygon block have differing node counts, and each element's
node count is compared as well.
([idaholab/moose#34526](https://github.com/idaholab/moose/pull/34526))
### MooseDocs slideshows

The MooseDocs gallery extension gained `!slideshow` and `!slide`, which present a set of images as
an automatically scrolling slideshow that stops when the viewer selects an image. Interface kernels
on a mesh with disjoint neighbor pairs, which [BreakMeshByBlockGenerator.md] creates, are also
documented now.
([idaholab/moose#33989](https://github.com/idaholab/moose/pull/33989),
[idaholab/moose#34315](https://github.com/idaholab/moose/pull/34315))

### Testing SQA coverage

CIVET now enforces the testing SQA documentation requirements for the phase field, porous flow,
chemical reactions, combined, and shifted boundary method modules, whose missing and duplicated
requirements were filled in first. The 151 CSG unit tests also left the legacy unit test manifest
with full requirement, design, and issue metadata.
([idaholab/moose#34294](https://github.com/idaholab/moose/pull/34294),
[idaholab/moose#34307](https://github.com/idaholab/moose/pull/34307),
[idaholab/moose#34365](https://github.com/idaholab/moose/pull/34365))

### Non-unity builds link through a response file

The non-unity `moose_LIB` link command is written to a response file rather than passed on the
command line. For an application the size of Cardinal, one object file per source file can exceed
the kernel's 128 KiB single-argument limit, and a parallel build can still route the recipe through
`bash -c`, which then fails with "Argument list too long". A non-unity build without NEML2 also
compiles again.
([idaholab/moose#34318](https://github.com/idaholab/moose/pull/34318),
[idaholab/moose#34441](https://github.com/idaholab/moose/pull/34441))

## MOOSE Bug Fixes

### Quadrature nodes survive a node-to-element map rebuild

`MooseMesh::possiblyRebuildNodeToElemMap` dropped the node-to-element entries that
`addQuadratureNode()` had made, because quadrature nodes are not part of the libMesh mesh. Such a
node is then tracked only while its patch reaches the processor that owns it, so near a processor
boundary it stopped being updated and kept the gap distance from the first step. An input combining
kinematic mechanical contact with `ThermalContact` and `quadrature = true` therefore showed
temperature hot spots at processor boundaries under large tangential motion.
([idaholab/moose#34517](https://github.com/idaholab/moose/pull/34517))

### Jacobian correctness

- `ADRankTwoCartesianComponent` extracted the component from `MetaPhysicL::raw_value` of the tensor,
  discarding its derivatives, so any residual depending on a stress or strain component had an
  incomplete Jacobian. The component now comes from the AD tensor directly; values are unchanged.
  ([idaholab/moose#34501](https://github.com/idaholab/moose/pull/34501))
- [ADFunctionNeumannBC.md], [ADVectorFunctionNeumannBC.md], and [ADFunctionPenaltyDirichletBC.md]
  evaluated their `Function` at the `Real` quadrature points. With `use_displaced_mesh = true` those
  points move with the displacements, so the Jacobian missed the derivative of a position-dependent
  function value: on a 2x2 QUAD4 mesh with `function = '1 + x + y'`, `||J - Jfd||/||J||` was 0.11,
  0.13, and 0.21. They now use the AD quadrature points there. Relatedly,
  `Function::value(ADReal, ADPoint)` called `timeDerivative()` even for a time without derivatives,
  so a function such as `ParsedGradFunction` that does not implement it failed at points carrying
  derivatives.
  ([idaholab/moose#34484](https://github.com/idaholab/moose/pull/34484))
- Four errors in phase field kernels were corrected: [ACInterfaceKobayashi1.md] and
  `ACInterfaceKobayashi2` were missing the `dL/dop` term in the diagonal Jacobian, `CHInterfaceBase`
  used the gradient of the wrong coupled variable in its `d2M/dargdarg` off-diagonal term,
  [ACInterface.md] used `dkappa/dop` instead of `dkappa/darg` in the `variable_L` off-diagonal
  Jacobian, and `ADACBarrierFunction` did not reset the sum of `eta_j^2` per order parameter, giving
  a wrong AD residual for three or more order parameters.
  ([idaholab/moose#34326](https://github.com/idaholab/moose/pull/34326))
- [DerivativeTwoPhaseMaterial.md] returned `h'(eta) d2F_b + (1 - h'(eta)) d2F_a` for the mixed third
  derivative with one order parameter and two composition arguments, where the free energy
  `F = (1 - h) F_a + h F_b + W g` gives `h'(eta) (d2F_b - d2F_a)`. The error is exactly `d2F_a` and
  does not vanish with `h'`, so it was present even in the bulk of phase a, where the exact value is
  zero. Reported by the community.
  ([idaholab/moose#34463](https://github.com/idaholab/moose/pull/34463))

### Solver diagnostics and convergence setup

- The SNES converged reason reported `SNES_CONVERGED_FNORM_ABS` whenever a MOOSE `Convergence`
  object converged and `SNES_DIVERGED_DTOL` whenever it diverged, so `-snes_converged_reason` named
  a criterion that may not have been the one that fired. The statuses now map to
  `SNES_CONVERGED_USER` and `SNES_DIVERGED_USER`.
  ([idaholab/moose#34367](https://github.com/idaholab/moose/pull/34367))
- [ReferenceResidualConvergence.md] did not check that the names in `group_variables` are variables
  of the nonlinear system, and it counts the groups in unsigned arithmetic. One unknown name gave
  zero groups and a segfault, and two or more underflowed to about 4e9 groups and exhausted memory,
  showing only `Initializing Convergence objects...`. This is easy to hit when switching a
  frictional contact input to `model = frictionless` with the tangential multipliers still listed.
  ([idaholab/moose#34446](https://github.com/idaholab/moose/pull/34446))
- `paramInfo` went through `mooseDoOnce`, so only the first of several messages was printed.
  ([idaholab/moose#34494](https://github.com/idaholab/moose/pull/34494))
- A fixed point iteration loop now registers postprocessor values at the start of the loop, so the
  initial, pre-solve value is no longer missing from the recorded history.
  ([idaholab/moose#34464](https://github.com/idaholab/moose/pull/34464))
- `GrainForceAndTorqueSum`, `PODReducedBasisTrainer`, and `PODReducedBasisSurrogate` crashed when
  `execute_on` included `INITIAL`, because the data they read did not exist yet; each now errors
  naming the missing data.
  ([idaholab/moose#33326](https://github.com/idaholab/moose/pull/33326))

### Mortar robustness

- In 2D, mortar nodal tangents came from `householderTangents`, which flips the sign of both
  tangents in a small cone around `n = -x`. The tangential Lagrange multiplier is stored along that
  tangent, so a Newton iterate that moved a secondary normal across the cone reversed the multiplier
  mid-solve, and 2D frictional mortar solves failed whenever a secondary normal was close to `-x`.
  The new `Moose::Mortar::nodalTangents` instead returns `e_z x n` and `e_z` in 2D, after Gitterle
  et al. (2010). Of 26 orientations of a frictional bouncing-block problem, 12 of the 20 in the -92
  to -88 degree band previously failed 1 to 7 solves; all now converge. Away from `-x` the 2D
  tangent equals the previous one to round-off.
  ([idaholab/moose#34146](https://github.com/idaholab/moose/pull/34146))
- Mortar penalty contact assembled Jacobian entries outside the preallocated sparsity pattern on
  some partitions, so PETSc reallocated the matrix and inputs with
  `error_on_jacobian_nonzero_reallocation = true` aborted. A secondary node's penalty pressure comes
  from its weighted gap over every secondary face touching the node, and a process that only ghosted
  such a face never learned its primary couplings; each process now asks that face's owner for them.
  ([idaholab/moose#34068](https://github.com/idaholab/moose/pull/34068))
- Dual mortar needs a positive weight at every secondary node, which the QUAD8 and TRI6 faces of
  HEX20 and TET10 meshes do not have; libMesh now builds the dual basis there against the
  transformed basis of Popp et al. (2012). The Petrov-Galerkin approach cannot use that fix, because
  it weights the gap with the standard basis, and on a partially open HEX20 or TET10 interface the
  combination does not converge. Mortar constraints and `LMWeightedGapUserObject` now error for
  `use_petrov_galerkin = true` with a `SECOND` order dual multiplier on such faces, including under
  the [Contact](syntax/Contact/index.md) action, and the
  [transformed dual basis](syntax/Constraints/Transformed_dual_basis_for_higher_order_mortar.md) has
  a documentation page.
  ([idaholab/moose#33560](https://github.com/idaholab/moose/pull/33560))

## MOOSE Modules Changes

### Contact module

Mortar and node/face mechanical contact now accept a rigid surface mesh, a block of surface
elements without volume elements behind them, as the primary side. See the
[Contact action documentation](syntax/Contact/index.md) for the input requirements.

The Cartesian Lagrange multiplier constraints, the dynamic mortar contact constraints, and the
thermal mortar gap constraints now linearize the secondary nodal normals and tangents, which
[idaholab/moose#33390](https://github.com/idaholab/moose/pull/33390) had added only for
standard-basis mortar contact. For a QUAD4 half-ring pressed onto a block and slid, frictionless
with Cartesian multipliers, `||J - Jfd||/||J||` drops from 2.2e-3 to 3.8e-4, matching the standard
basis; the rest is the mortar segment geometry, which no mortar formulation differentiates.
[ModularGapConductanceConstraint.md] now rejects `interpolate_normals = false`, which indexed the
nodal normals by quadrature point, and [GapConductanceConstraint.md] is that same constraint with a
built-in k/l flux and a plate gap, with unchanged parameters and residuals. Jacobians and iteration
counts change; converged solutions do not.
([idaholab/moose#34213](https://github.com/idaholab/moose/pull/34213))

The new [MortarContactForce.md] postprocessor reports the normal contact force on the secondary
surface of one mortar contact pair, as a component or a magnitude, taking that pair's weighted gap
user object. Per-pair forces previously needed a residual tag, `TagVectorAux` kernels, and a
`NodalSum` each, and a tag cannot be shared between pairs whose surfaces touch, so such inputs kept
one `[Contact]` block per pair.
([idaholab/moose#34358](https://github.com/idaholab/moose/pull/34358))

[MortarCZMDebondedBoundaryUpdater.md] builds sidesets on the fully debonded portions of a mortar
cohesive zone interface, on both the secondary and the paired primary faces, so that a load such as
a gas pressure can be applied to the walls of the void that opens. A segment counts as separated
when its damage reaches `threshold` at every quadrature point of the secondary lower-dimensional
element, and faces are only added, never removed.
([idaholab/moose#34284](https://github.com/idaholab/moose/pull/34284))

With `correct_edge_dropping = true`, [ComputeDynamicWeightedGapLMMechanicalContact.md] enforced the
persistency constraint with the wrong sign on the old gap rate, so nodes in persistent contact got a
gap rate of `-2*gdot_n` instead of zero, which flipped sign and grew each step until the solve
diverged. Results without `correct_edge_dropping` are unchanged.
([idaholab/moose#34486](https://github.com/idaholab/moose/pull/34486))

### Heat transfer module

[GapFluxModelPressureDependentConduction](GapFluxModelPressureDependentConduction.md) now obtains a
contact pressure from mechanical mortar contact through the new `contact_pressure_uo` parameter,
which names the mortar contact user object (`lm_weightedgap_object_<contact block name>` when the
Contact action creates it). The contact Lagrange multiplier variable can store a scaled pressure, so
inputs that coupled the normal contact multiplier should replace
`contact_pressure = <normal multiplier>` with `contact_pressure_uo = <contact user object>`.

[MortarFrictionalWorkWearAux](MortarFrictionalWorkWearAux.md) (formerly `MortarArchardsLawAux`)
follows the same pattern: it takes the mortar contact user object through the new `weighted_gap_uo`
parameter. Replace `normal_pressure = <normal multiplier>` with
`weighted_gap_uo = <contact user object>`. The object is renamed because its wear law, wear
proportional to frictional work, is Reye's (1860); `MortarArchardsLawAux` remains a deprecated alias
until 06/30/2027.

Both read the physical nodal pressure through the new framework interface
`MortarContactPressureProvider`, which `WeightedGapUserObject` implements. In support of it,
`PRE_AUX` user objects now run on `linear` and `nonlinear` after the displaced and mortar mesh
update, where they previously computed on the displaced mesh of the previous evaluation. This
affects every application.
([idaholab/moose#34184](https://github.com/idaholab/moose/pull/34184))

### Solid Mechanics module

- With F-bar stabilization and large kinematics, the Lagrangian stress materials defined by a first
  or second Piola-Kirchhoff stress converted it to the Cauchy stress with the unstabilized
  deformation gradient `F` instead of the stabilized `Fbar`. Where `J = det F` varies within an
  element the residual stress was off by `(Jbar/J)^(2/3)` for [ComputeLagrangianStressPK1.md]
  materials and `(Jbar/J)^(1/3)` for [ComputeLagrangianStressPK2.md] materials, up to 7% for one
  large-strain HEX8, and the Jacobian was inconsistent with the kernels' non-local F-bar term.
  `Fbar` now replaces `F` in the constitutive model alone, after de Souza Neto et al. (1996).
  Residuals change for such materials; Cauchy-stress materials, small kinematics, and runs without
  F-bar are unchanged.
  ([idaholab/moose#34327](https://github.com/idaholab/moose/pull/34327))
- The Lagrangian stress divergence kernels and `ComputeLagrangianStrain` both take
  `stabilize_strain` and `F_bar_mode`, and nothing checked that they agree, so setting either on
  only one object silently changed the residual and gave a Jacobian with a relative error of about
  6e-2. A mismatch is now a `paramError` at setup, as it already was for `large_kinematics`.
  ([idaholab/moose#34476](https://github.com/idaholab/moose/pull/34476))
- [ComputeSimoHughesJ2PlasticityStress.md] builds its elastic predictor from the incremental
  deformation gradient, which is the identity with small kinematics, so the material had no shear
  stiffness and never yielded: uniaxial tension gave zero axial stress instead of `E*eps`. It is a
  finite-strain formulation, so it now errors when the strain calculator uses small kinematics.
  ([idaholab/moose#34490](https://github.com/idaholab/moose/pull/34490))
- [ElementJacobianDamper.md] checked the trial Newton update in the wrong direction: the solver
  applies `new = old - damping * update`, but the damper moved the displaced mesh by
  `+damping * update`, so an update that inverts an element was accepted undamped while one that
  only stretches an element could be damped. It now limits the steps that invert elements.
  ([idaholab/moose#34451](https://github.com/idaholab/moose/pull/34451))

### Shifted Boundary Method module

The Shifted Cohesive Zone Method enables cohesive zone simulations on structured voxel-based
meshes that are not fitted to the interface. The new shifted interface kernels,
[SCZMInterfaceKernelSmallStrain.md] and its AD variant, impose the interface condition weakly on a
surrogate interface formed by element sides, using the distance vector and true normal to shift the
condition onto it. The [ShiftedCohesiveZoneAction.md] action sets up the required kernels,
materials, and geometry objects, supported by the new [SubdomainGrainIDGenerator.md] and
[SubdomainInterceptedGenerator.md] mesh generators and [SBMInterfaceManager.md] user object.
([idaholab/moose#33667](https://github.com/idaholab/moose/pull/33667))

### Navier-Stokes module

- The linear finite volume segregated (SIMPLE) solver gained input syntax for the porous medium
  capability through the new `[Physics/NavierStokes/SolidHeatTransferSegregated]` block,
  [PNSLinearFVSolidHeatTransferPhysics.md], alongside the flow, fluid heat transfer, and scalar
  transport Physics; the objects were previously reachable only by manual syntax.
  ([idaholab/moose#34488](https://github.com/idaholab/moose/pull/34488),
  [idaholab/moose#31999](https://github.com/idaholab/moose/pull/31999))
- Turbulent temperature wall functions are available to the linear finite volume solver through the
  new [LinearFVTemperatureWallFunctionBC.md] and [EffectiveTurbulentThermalConductivityAux.md].
  ([idaholab/moose#32537](https://github.com/idaholab/moose/pull/32537))
- [LinearFVTurbulentTimeDerivative.md] skips the time derivative on elements touching a boundary in
  its `walls` list, matching `LinearFVTurbulentAdvection` and `LinearFVTurbulentDiffusion`, so the
  near-wall rows are left to the algebraic wall treatment of the `k-epsilon` source kernels.
  ([idaholab/moose#34277](https://github.com/idaholab/moose/pull/34277))
- Auxiliary fields the segregated equations depend on, such as the turbulent viscosity, used
  `execute_on = NONLINEAR`, which the linear segregated solver triggers on every system assembly,
  several times per outer iteration. That solver now also executes
  `MULTISYSTEM_FIXED_POINT_ITERATION_END` once per outer iteration, and the turbulence Physics put
  their auxiliary kernels on that flag plus `TIMESTEP_BEGIN`.
  ([idaholab/moose#34512](https://github.com/idaholab/moose/pull/34512))
- [PNSFVSolidHeatTransferPhysics.md] treats `thermal_conductivity_solid` as the effective solid
  conductivity of the documented solid energy equation. It previously built the scalar conduction
  term with `PINSFVEnergyDiffusion` at its default `effective_conductivity = false`, which
  discretizes `div(eps k_s grad T_s)` with `eps` the fluid fraction; the term now uses `FVDiffusion`
  or `FVAnisotropicDiffusion`, which do not involve the porosity. Results change for inputs with a
  scalar solid conductivity and `eps != 1`, where the temperature rise of a heated slab was too
  large by `1/eps`. The parallel conduction approximation is now entered directly.
  ([idaholab/moose#34449](https://github.com/idaholab/moose/pull/34449))
- The new [TorchScript1DProfileFunctorMaterial.md] turns a TorchScript model that predicts a
  one-dimensional spatial profile into named functors, mapping each physical point to a profile
  coordinate through a configurable origin, direction, and scale and interpolating linearly between
  the given `profile_coordinates`. It is aimed at closure quantities such as friction and heat
  transfer coefficients. The model is evaluated once at initial setup, and the functors give values
  only, since TorchScript inference is not part of MOOSE's AD graph.
  ([idaholab/moose#33552](https://github.com/idaholab/moose/pull/33552))

### Thermal Hydraulics module

The path-integrated incompressible flow model gained conjugate heat transfer through pipe walls.
[ADPipeInnerWallTemperatureScalarKernel.md] couples the wall to the flow with the
[ADDittusBoelterHTCFunctorMaterial.md] correlation, and the outer wall takes an ambient temperature,
a coupled convective temperature, a heat flux, or radiation through the corresponding scalar
kernels.
([idaholab/moose#33957](https://github.com/idaholab/moose/pull/33957))

### Fluid Properties module

- [NASA7IdealGasFluidProperties.md] gained viscosity and thermal conductivity, and
  [IdealGasMixtureFluidProperties.md] the Wilke and Mason-Saxena mixing rules through
  `transport_mixing_rule` and Chapman-Enskog binary diffusion coefficients through
  `binaryDiffusionCoefficient`, with components supplying their Lennard-Jones parameters. These
  gases can therefore now be used in the thermal hydraulics module's gas-mixture flow channels,
  through the new [FluidPropertiesBinaryDiffusionCoefMaterial.md]. The density from pressure and
  entropy, which single-phase stagnation inlets and compressors require, was also added.
  ([idaholab/moose#34257](https://github.com/idaholab/moose/pull/34257))
- He, Ar, Kr, and Xe were added as NASA 7-coefficient species, so they can be components of
  [IdealGasMixtureFluidProperties.md]. Helium takes the Petersen viscosity and conductivity from
  [HeliumFluidProperties.md], because Chapman-Enskog is 6% low at 1000 K.
  ([idaholab/moose#34336](https://github.com/idaholab/moose/pull/34336))
- Evaluating each component's entropy at its partial pressure gives NaN for a mass fraction of
  exactly zero. Since the contribution tends to zero with the molar fraction, absent components are
  now skipped in the ideal gas mixture entropy.
  ([idaholab/moose#34314](https://github.com/idaholab/moose/pull/34314))

### Porous Flow module

[PorousFlowPorosityVinsomeWesterveld.md] takes an optional `matrix_thickness` `L`. The material
assumed a semi-infinite matrix, so the heat content, and hence the thermal opening of a
lower-dimensional fracture, kept growing as `sqrt(t)` under a constant fracture-face temperature,
where in practice only the rock within about half the fracture spacing should contribute. Given `L`,
the opening uses the heat content of the layer `0 <= z <= L`, which is bounded and stays linear in
temperature, so the Jacobian remains exact. Without the parameter, results are unchanged.
([idaholab/moose#34251](https://github.com/idaholab/moose/pull/34251))

### Subchannel module

- The new [SCMTriCoreMeshGenerator.md] and [SCMQuadCoreMeshGenerator.md] place SCM assemblies on a
  hexagonal or rectangular core lattice and merge them into one mesh, so a full core can be built in
  a single input. Each takes assembly, duct, or 3D visualization assembly meshes as `inputs` and a
  `pattern` of indices with -1 for empty positions. Assemblies may differ in size and pin count, any
  pair whose ducts would overlap is rejected, and every block and boundary of placed assembly k gets
  the suffix `_k` while each element records k in the `assembly_id` extra element integer.
  Assemblies are not connected, so there is no crossflow between them. A core of 1D assemblies can
  only be generated with `--mesh-only` for now, because the 1D generators still write their
  connectivity into a single `SubChannelMesh`.
  ([idaholab/moose#34424](https://github.com/idaholab/moose/pull/34424))
- `SCMDetailedTriAssemblyMeshGenerator` and `SCMDetailedQuadAssemblyMeshGenerator` build 3D meshes
  used only to visualize SCM results, so they are renamed
  [SCMTriVisualizationAssemblyMeshGenerator.md] and
  [SCMQuadVisualizationAssemblyMeshGenerator.md]. The old names remain deprecated aliases until
  06/30/2027.
  ([idaholab/moose#34469](https://github.com/idaholab/moose/pull/34469))
- [SubChannelPointValue.md] and [SCMPinSurfaceTemperature.md] reject a subchannel or pin `index`
  outside the mesh with a `paramError` naming the valid range, instead of crashing or reporting a
  value from an unrelated location, and `SCMPinSurfaceTemperature`, [SCMPlanarMean.md], and
  `QuadSubChannelNormalSliceValues` reject a `height` below the inlet, which used to return zero.
  ([idaholab/moose#34504](https://github.com/idaholab/moose/pull/34504))
- `staggered_pressure` is deprecated and ignored. Pressure is a face value and `DP` a cell value, so
  `P_{k-1} = P_k + DP_k` is exact; the option staggered nothing and instead averaged the pressure
  drop of neighboring cells, inconsistently across solver paths, giving a total drop of 26888 Pa
  against 29832 Pa on one validation input.
  ([idaholab/moose#34245](https://github.com/idaholab/moose/pull/34245))

### Phase Field module

[GrainTracker.md] now treats order parameter values within `libMesh::TOLERANCE` as equal when
choosing which grain owns an entity, breaking ties by the lower grain ID. Entities on an interface
can have equal values for two grains and the solve resolves those ties only to round-off, so
ownership previously depended on the number of processors.
([idaholab/moose#34022](https://github.com/idaholab/moose/pull/34022))
